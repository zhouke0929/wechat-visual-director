# 公众号文章输入协议

将文章保存为 UTF-8 Markdown，最大 2 MiB。不得包含密钥、Cookie、Token、脚本、表单、外部样式表或用于排版的自定义 HTML。

## 最小结构

```markdown
---
schema_version: wechat_article.v1
title: 高考志愿填报前，先看懂这三个规则
article_type: tutorial_steps
summary: 帮助家长核对分数、位次和专业限制。
---

# 高考志愿填报前，先看懂这三个规则

一段明确导语。

## 第一步：核对分数与位次

正文内容。

1. 保存官方查询页面；
2. 记录准确位次；
3. 标记专业限制。

> 数据来源：省级教育考试院当年公开信息。
```

## 结构规则

- 只使用一个 H1 作为文章标题，且与 frontmatter `title` 一致。
- H2 表示主章节，视觉编译器不得把它吞进概念卡或证据卡。
- H3 表示章节内概念、问题、步骤或小主题；普通强调句不要升级为标题。
- 并列信息用无序列表；有先后关系的操作用有序列表。
- 真实二维数据才使用表格，不用表格模拟布局。
- 只把真正需要读者记住的短语写成 `**重点短语**`。同一段最多一处，全文通常 3–5 处；不要加粗整段。
- 只在内容发生明显转场时单独写一行 `---`，全文通常不超过 2 处；不要在每个 H2 前后机械添加。
- 已有图片使用 `![可直接作为图注的准确语义](path-or-url)`；可靠的 alt 会显示为低强调图注。没有图片时不要插入随机占位地址，也不要为模型生成图编造图注。

## 组件友好的语义表达

Markdown 只描述内容结构，不写组件名、主题名、分割线样式或视觉指令。视觉主编根据下列真实语义决定是否使用组件：

- 在提交预检前做一次语义整理。若正文已经用“第一、第二、第三”“一方面、另一方面”或连续小标题表达多个独立要点，应改成对应的 Markdown 列表；不要把真实并列关系继续埋在长段落里。
- 真正的概念解释：使用 H3 概念标题，下一段紧接定义；普通章节标题不要伪装成概念。
- 有先后顺序的步骤：使用 3–5 项有序列表，序号由列表顺序动态生成。
- 并列观点或行动项：使用 2–6 项无序列表，不要把连续正文机械拆成列表。
- 前后变化或二选一对比：使用至少 2 项的同一列表，并在原文中明确“之前/之后”或两个比较对象。
- 需要突出且有来源的原话或判断：使用 Markdown 引用 `>`；数据来源段仍写明“数据来源：”。
- 风险、限制和注意事项：直接写清原文事实，不为了获得警示组件补造结论。

长篇 `data_policy`、`viewpoint_trend` 或 `tutorial_steps` 文章若包含大量段落，却没有 H3、列表或真实表格，系统会返回 `source_structure_too_flat`。此时只整理已有关系：

- 多个真实因素、政策信号或读者判断 → 列表；
- 有明确顺序的流程 → 有序列表；
- 同一指标下多个地区、年份或对象 → 表格；
- 一个需要解释的真实术语 → H3 与紧随定义段。

不要为了通过预检给叙事段落随意编号，也不要把一维数据硬凑成表格。导语不应完整复述第一章已经承担的事件说明。

组件、章节线、行内重点、图片外框和品牌页尾均由确定性渲染器按主题生成。`---` 只声明“此处需要内容转场”，不声明线条样式。更换或新增视觉主题时，不需要修改 `wechat_article.v1`，也不得让宿主 Agent 输出 HTML。

## 文章类型

- `data_policy`：数据、政策、规则解释。
- `viewpoint_trend`：观点、趋势、行业观察。
- `tutorial_steps`：教程、步骤、操作清单。
- `lively_growth`：成长故事、校园与活动内容。
- 无法可靠判断时省略 `article_type`，让系统识别。

## 内容边界

- 可以整理明确的层级、列表和段落，可以润色但不得改变事实含义。
- 来源不确定时标记“待人工核验”，不得编造来源或链接。
- 不把场景句误标为结论，不把核心功能或主章节伪装成概念解释。
- 不指定组件名称、颜色、HTML 或 CSS；视觉系统根据语义和历史避重决定。
