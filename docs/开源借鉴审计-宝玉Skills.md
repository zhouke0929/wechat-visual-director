- 审计日期：2026-08-10
- 上游仓库：[JimLiu/baoyu-skills](https://github.com/JimLiu/baoyu-skills)
- 锁定提交：`6b7a2e417500561a5ecdd0b168332f4142584617`

## 1. 结论

不把宝玉 Skills 整套嵌入 Visual Director，也不新增 Bun 运行时和第二套配置体系。

值得吸收的是它对图片任务的拆解方式、Provider 能力矩阵、批量生成与浏览器交付思路；这些能力应改写成 Visual Director 现有架构中的受控模块，继续服从以下边界：

1. 宿主 Agent 只输出结构化视觉意图，不自由生成最终 HTML/CSS。
2. Python 核心继续负责 Schema 校验、主题避重、组件编译、图片状态和发布门禁。
3. 公众号官方 API/Wenyan 仍是首选草稿链路，浏览器交付只做可选兜底。
4. 图片候选必须人工确认，任何浏览器自动化也只保存草稿，不自动群发。
5. 不为了“支持更多模型”一次性引入用户当前没有使用的 Provider。

## 2. 四个模块的处理方式

### 2.1 `baoyu-infographic`

| 项目 | 决策 |
|---|---|
| 内容分析框架 | **借鉴并重新实现**。引入“学习目标、受众、复杂度、事实锚点、视觉机会”五类字段。 |
| Layout × Style 分离 | **借鉴并重新实现**。信息结构与审美风格分层，避免提示词把布局、颜色和装饰混成一团。 |
| 21 种布局 × 22 种风格 | **不整体导入**。首轮只选与教育公众号高频内容相符的 6–8 种结构。 |
| 事实原样锁定 | **采用**。数字、日期、政策名、机构名和引用进入不可改写的事实区。 |
| 每次推荐 3–5 组并强制确认 | **不采用**。与当前“少确认、快速交付”的运营路径冲突。 |
| Prompt 文件留档 | **采用思想**。每个图片槽保存可复现的 `visual_intent`、Provider 编译结果和版本号。 |

首批候选结构：线性进程、二元对比、比较矩阵、层级关系、中心辐射、结构拆解、便当网格、路径/桥接。它们是内部语义枚举，不直接复制上游版式文件。

### 2.2 `baoyu-article-illustrator`

| 项目 | 决策 |
|---|---|
| Type × Style × Palette | **借鉴并重新实现**。Type 表示图片的信息作用，Style/Palette 必须受当前文章主题约束。 |
| 先判断插图位置和用途 | **采用**。只有“图片能降低理解成本或建立情绪入口”的段落才创建图片槽。 |
| 视觉隐喻优先于逐句直译 | **采用**。氛围图表达文章概念与情绪，不把正文句子机械画成图。 |
| `outline.md` + 每图 Prompt | **改造成数据库资产**。不额外要求运营管理文件夹，但交付包可以导出。 |
| 默认手绘教育风格 | **不采用**。固定默认会重新制造同质化；风格由主题、文章类型和最近历史共同决定。 |
| 每次都询问密度、风格、配色 | **不采用**。默认自动推荐，工作台只保留换图、重生成和人工上传。 |

Visual Director 的图片 Type 首轮保持精简：`structural_infographic`、`comparison`、`timeline_or_flow`、`concept_scene`、`atmosphere`、`cover`。每个 Type 使用独立 Prompt 编译器，不能共享一段万能提示词。

### 2.3 `baoyu-image-gen`

| 项目 | 决策 |
|---|---|
| Provider 能力矩阵 | **借鉴**。明确模型是否支持参考图、比例、分辨率、批量和响应格式。 |
| 批量任务、并发限制、失败项重试 | **借鉴并在 Python 层实现**。只重试失败图片，不重新生成已采用候选。 |
| Seedream 型号和尺寸校验 | **作为测试参考**。结合供应商官方文档维护自己的适配器。 |
| 整套 TypeScript/Bun 适配层 | **不引入**。会增加安装体积、首次启动风险和跨平台故障面。 |
| 自动选择任意已配置 Provider | **暂不采用**。用户明确选择的 Provider 优先，避免意外费用和输出漂移。 |
| Codex CLI 生图桥接 | **后续可选实验**。不能作为跨 Agent 的默认能力。 |

当前优先保持三类生产适配：Seedream、Gemini/Nano Banana、OpenAI Images 兼容接口。新增 Provider 必须先通过相同文章、相同视觉意图的回归样本。

### 2.4 `baoyu-post-to-wechat`

| 项目 | 决策 |
|---|---|
| 官方 API 草稿链路 | **保持现状**。当前 Wenyan 适配已经完成真实生产验证，不在本轮替换。 |
| Chrome CDP 浏览器草稿链路 | **列为可选兜底**。适合无 API 权限或 IP 白名单不便配置的用户。 |
| 图片占位符逐张替换 | **仅借鉴交互流程**。若开发浏览器适配器，需要重新实现并增加结果核验。 |
| 多账号、SSH 远程出口 | **暂不采用**。超出当前个人开源作品与内部运营的主要场景。 |
| API、浏览器、复制三层降级 | **采用为能力矩阵**：官方 API优先，浏览器可选，富文本复制/交付包保底。 |
| 自动群发 | **明确不采用**。所有路径的终点都是公众号草稿箱。 |

浏览器自动化不能替代现有幂等门禁。页面变化、登录态失效或保存结果不明确时，必须返回“待人工核对”，不能静默重试制造重复草稿。

## 3. 合规处理

当前审计只吸收思想和公开接口行为，不复制上游代码或大段 Prompt，因此不需要把上游许可证正文加入发行包。

后续若发生以下任一情况，必须在同一提交中新增或更新 `THIRD_PARTY_NOTICES.md`：

- 复制或翻译上游 Prompt 的实质性段落；
- 移植 Provider、浏览器发布或图片处理代码；
- 复制测试夹具、配置 Schema 或样式定义；
- 将上游文件修改后随本项目分发。

记录项至少包括：项目名、仓库 URL、锁定 commit、原文件路径、许可证、修改说明。MIT 代码可以与 Apache-2.0 项目共同分发，但必须保留原版权与许可文本。第三方图片、字体和外部模型服务仍分别遵守其自身条款。

## 4. 分阶段实施清单

### P0：图片规划与 Prompt 编译器 V2

1. 给每个图片槽增加 `visual_role`、`learning_objective`、`fact_anchors`、`layout_family`、`style_treatment`、`palette_intent`。
2. 将结构信息图、氛围图和封面拆成独立编译路径。
3. 保存供应商无关的视觉意图与供应商专用 Prompt，便于换模型和复盘。
4. 强制事实锁定、安全区、移动端可读性与禁止伪造品牌/二维码。

### P1：小型信息图结构库

只落地 6–8 种高频结构，并根据文章语义选择，不向运营暴露 21×22 的选择矩阵。结构库先服务 Seedream 实测，再分别评估 Nano Banana 与 GPT Image。

### P1：图片任务执行质量

增加失败项单独重试、Provider 能力校验、批次结果摘要和 Prompt 版本追踪。默认仍串行，只有同一任务存在多张已定稿 Prompt 时才允许受控并发。

### P2：浏览器草稿兜底探针

先制作独立技术探针，不进入默认安装包。验收 Chrome 登录复用、HTML 粘贴、图片替换、标题/摘要保持、草稿保存回执和未知结果门禁，再决定是否成为正式适配器。

### 暂不实施

- 整体依赖 `baoyu-skills` 或 Bun；
- 一次性支持所有图片供应商；
- 21×22 可视化选择器；
- 多账号管理与 SSH 远程发布；
- 浏览器自动群发；
- 在未完成对照评测前替换现有 Wenyan 链路。

## 5. 验收设计

使用 3 篇真实或拟真长文覆盖政策解读、步骤教程、观点趋势，每篇固定相同正文和图片槽，对比当前 Alpha.17 与 V2：

| 指标 | 通过标准 |
|---|---|
| 图文语义匹配 | 运营能解释每张图为何出现在该段，不是泛化装饰图 |
| 信息准确 | 数字、日期、专有名词无遗漏、改写或新增 |
| 移动端完整性 | 标题、节点和边缘插画无裁切，关键文字可读 |
| 主题协调 | 图片配色与文章主题协调，但不要求整篇只有一种颜色 |
| 图片采纳率 | 6 张候选中至少 4 张可直接采用或只需一次重生成 |
| 人工时间 | 图片审核与替换不高于现有 NotebookLM 手工链路 |
| 稳定性 | 单张失败不影响其他候选，不产生重复计费或重复草稿 |

若 P0 对图片采纳率没有明显提升，不继续扩充布局数量，优先更换模型或调整视觉意图编译器。

## 6. P0 落地记录

P0 已在现有 Python 核心中落地，未引入 Bun 或第二套运行时：

1. 新增供应商无关的 `image_visual_intent.v3`，在 V2 的视觉作用、学习目标、事实锚点、布局族、风格与配色之上，增加场景隐喻、空间区域、节点视觉、连接语言、装饰语法与文字模式。
2. 首批启用 `linear_progression`、`binary_comparison`、`comparison_matrix`、`hierarchical_layers`、`hub_spoke`、`structural_breakdown`、`timeline`、`pathway` 与氛围图专用 `semantic_scene`。
3. 布局先从原文结构确定；宿主 Agent 的建议只有与原文关系兼容时才被采用，弱模型不能把“步骤”误改成“时间线”或把“对比”改成普通卡片。
4. `fact_anchors` 必须逐字来自图片槽绑定的正文块；长节点只绘制连续原文短标签，完整事实仍留在文章和审计字段中，Provider 不得改写数字、日期、政策名或结论。
5. Seedream 和 OpenAI Images 兼容路径使用同一视觉脚本、不同供应商编译语言；旧任务缺少 V3 字段时会按原有事实引用补齐，避免升级后历史任务失效。
6. 工作台图片卡片显示“视觉作用 + 布局 + 学习目标 + 场景隐喻”，不增加新的强制确认步骤。

三篇拟真长文的结构抽样结果已经覆盖：线性步骤、二元对比、中心辐射、结构拆解和氛围场景。下一步不是继续堆布局，而是用 Seedream 对同一批正文做真实生图盲评；只有图片采纳率达到验收线，才进入 P1 的批次重试和更多布局扩展。
