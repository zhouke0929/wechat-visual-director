# 公众号视觉主编组件视觉质量基线 V1.0

| 项目 | 内容 |
|---|---|
| 状态 | 生效，后续组件设计与评审必须遵守 |
| 生效日期 | 2026-07-15 |
| 产品负责人 | 徐均舸 |
| 适用范围 | 组件画廊、Agent 视觉方案、微信正文渲染 |

## 1. 目标

这份基线用于保证后续组件达到稳定的视觉质量下限，而不是依赖某一次临场发挥。所谓“漂亮”必须同时满足：语义关系清楚、第一眼有重点、具有视觉记忆点、与最近内容不过度重复，并能稳定渲染到微信正文。

## 2. 五条强制原则

1. **先表达关系，再添加装饰。** 每个组件必须对应明确语义，例如提问、编号、证据、前后变化、逻辑路径或概念解释。
2. **差异不能只靠换颜色。** 新变体必须在轮廓、结构、空间节奏、视觉隐喻中至少改变两项。
3. **不把通用蓝色作为默认答案。** 蓝色可以使用，但必须由品牌或内容语义支持，不能因为“安全”而统一使用蓝色框、蓝色线和蓝色标题。
4. **稳定品牌，轮换视觉。** 品牌名称、正文可读性、固定 CTA 等保持稳定；组件结构、强调色和装饰节奏在最近 5 篇历史窗口内主动避免重复。
5. **模型不直接写自由 HTML。** Agent 只选择语义、内容块和已批准变体；HTML、样式、降级规则由确定性组件库生成。

## 3. 单组件设计要求

- 每个新组件至少提供 2 个真正不同的变体，不接受只换颜色的伪变体；
- 读者应在 5 秒内说出组件表达的问题、顺序、对比或结论；
- 视觉重点必须落在原文事实或观点上，装饰不能喧宾夺主；
- 同一组件中的所有正文必须完整可见，不得通过透明、裁切或颜色造成信息丢失；
- 颜色不能成为唯一信息通道，必须同时使用编号、标题、位置、线条或形状；
- “统一配色”不等于把所有颜色调成相近的灰度或明度；主色、点缀色与浅底色必须拉开层级，避免棕金、灰绿等中间色互相混浊；
- 丰富度来自轮廓、留白、编号徽标、细线、圆点和局部错位等受控细节，不依赖大面积渐变或随机宽度色块；
- 装饰元素不得暗示原文中不存在的数据、排名、因果或权威来源；
- 组件必须有清晰的微信不兼容降级方案，降级后不能丢失文本和信息顺序。

## 4. 整篇文章的组合要求

- 一屏最多使用 2 个强强调组件，避免所有段落都在争夺注意力；
- 连续两个章节不重复使用完全相同的强调结构；
- 最近 5 篇文章中高频出现的主色、标题轮廓和装饰图形应降低选择权重；
- 内容型品牌一致性主要由表达语气、事实质量、固定 CTA 和基础 Token 保证，不要求每篇使用相同主题组件；
- 固定小程序 CTA 属于数字资产，不参与视觉新鲜度轮换，并支持后续版本替换。

## 5. 入库门槛

组件进入 Agent 候选库前必须全部通过：

| 检查项 | 通过标准 |
|---|---|
| 语义清晰度 | 产品负责人或运营能在 5 秒内说出信息关系 |
| 视觉重点 | 第一眼重点与设计意图一致 |
| 视觉记忆点 | 与旧模板相比，不只是换色或换圆角 |
| 变体差异 | 两个变体至少在两个视觉维度上不同 |
| 文本完整性 | 标题、正文、数字和符号无裁切、遮挡或隐形 |
| 移动端适配 | 375px 与 390px 无全局横向滚动 |
| 可访问性 | 正文对比度合格，颜色不是唯一信息通道 |
| 确定性渲染 | 相同结构化输入可得到稳定输出 |
| 微信兼容性 | 内联样式渲染或明确降级通过 |
| 人工意愿 | 产品负责人通过，运营愿意在真实文章中试用 |

## 6. 评审分工

- **产品负责人参与：** 问题定义、视觉方向、候选入库、运营反馈与版本范围；
- **运营参与：** 真实内容试用、第一眼重点、直接使用意愿和人工修改量；
- **技术侧负责：** CSS 与组件协议、微信兼容、响应式、自动化回归和降级策略；
- **Agent 负责：** 根据文章语义和最近 5 篇历史，提出允许的组件与变体组合，不越权修改组件代码。

## 8. 明确禁止的低质量模式

- 全文重复同一种圆角标题框；
- 把通用蓝色、青色渐变当作账号风格本身；
- 仅改变颜色就声称是第二套视觉方案；
- 为了“丰富”而给每一段增加装饰；
- 直接让模型生成整段不可控 HTML/CSS；
- 未经 390px 预览和移动端回归就进入公众号草稿；
- 因视觉效果删除、改写或遮挡原文事实。

## 9. 质量承诺边界

本基线能够稳定提高组件质量下限，但不能保证每次自动组合都达到资深设计师手工精修水平。因此正式生产仍保留人工确认，并持续记录组件采纳率、人工修改时间和被退回原因，用真实数据迭代组件库。

## 10. 2026-07-15 运营复评补充

首轮统一调色板将青绿、棕金和砖红压到相近的中等明度，虽然减少了颜色跳跃，却形成了“脏、闷、像系统标签”的新问题，并误删了一部分有价值的装饰细节。V0.2.1 改为高留白、深青绿正文锚点、明黄/珊瑚/天蓝局部强调；编号观点使用等宽内容列与独立编号徽标，定位外框改为低干扰青色。该反馈证明：组件数量控制与组件视觉质量必须分开评审，不得用减组件代替设计优化。

## 11. 2026-07-28 主题套件构图补充

同一主题不再等同于“所有组件使用同一种卡片”。主题一致性由字体层级、有限色板、线条粗细、装饰母题和留白节奏共同保证。

新增强制标准：

- 每套主题至少出现 6 种可辨认的空间轮廓；
- 完整文章中的卡片型强调不超过全部内容单元的 35%；
- 必须同时提供无完整容器的标题、行内强调、引用或边注；
- 必须提供图文过渡、章节分割和结尾 CTA；
- 同一主题内部的两个组件若只改变颜色、边框或圆角，视为同一形态；
- 样本册必须先以完整文章验证节奏，再逐项评审组件；
- 参考成熟编辑器时只抽象构图规律，禁止复制第三方专有模板、素材和代码。

## 12. 组件编号来源规则

- 组件中展示的章节编号必须来自解析后的真实章节顺序；
- 列表、步骤和路径编号必须来自组件实际绑定的内容项顺序；
- 原文标题已经带有显式编号时，不再重复添加自动章节号；
- “之前/之后”“基线/变化”等固定角色使用语义标签，不伪装成 `01/02` 内容编号；
- 禁止使用没有内容依据的 `00`、`01`、`03` 等纯装饰数字；
- 新增或修改主题时，自动测试必须扫描并阻止典型装饰性硬编码数字回归。
