# V1.0 主题扩展包系统：产品与技术决策

## 决策摘要

官方主题和用户主题统一进入主题注册表。用户主题采用声明式扩展包，复用文章语义和编辑契约。`design_system` 的基础参数仍是预设渲染，不应称为开放式新风格生成；新增的 `design_system.layouts` 允许 Agent 自行安排语义字段、容器和装饰节点，以结构自由度实现独立风格，不开放任意 HTML/CSS 或可执行模板。

当前版本交付包括：主题包契约、校验器、本机安装/删除/导出、CLI、API、主题样本册“官方主题 / 我的主题”分区、参数化主题编译器，以及宿主 Agent 根据文字描述或参考图生成主题包的 Skill 流程。参考图自动特征提取和可视化主题编辑器属于后续阶段；具备视觉能力的宿主当前可以归纳参考图特征，再映射到受控字段，但核心不会从图片自动生成 CSS。

## 问题背景

现有 12 套主题分两批实现，主题元数据、组件变体、Visual DNA、画廊渲染和 API 白名单分散在不同模块。继续以手写 HTML/CSS 扩展会带来三类风险：

1. 固定标签与正文文本节点结构不一致，导致部分主题不能原文编辑；
2. 同类组件的 hover、选区和可编辑范围不一致；
3. 新主题需要同时修改多处白名单，容易出现主题可展示但不能切换，或可切换但图片 DNA 回退。

## 核心原则

### 语义结构归核心所有

`question_hook`、`evidence_callout` 等 12 类组件的语义字段、正文绑定和编辑契约由核心维护。主题可以声明字段所在的布局树，由核心生成 DOM；不能加入 HTML、原始 CSS、JavaScript、可执行模板或渲染器，也不能新增文章正文。

### 主题包描述视觉 DNA 与独立设计系统

v1 主题包包含：

- 标识、名称、版本、作者和用途；
- 继承的官方 `base_theme`；
- 10 个确定性色板角色；
- 9 个 0–1 Visual DNA 维度；
- 材质标签、语气和人格描述；
- 可选的 `design_system`，用于生成不依赖官方主题 ID 的独立视觉语法；
- 旧版九角色 `style_recipe` 仅保留读取兼容，不再作为新建主题的默认路径；
- 固定的 12 组件覆盖清单与 `semantic_dom_v1` 编辑契约。

完整 JSON Schema 位于 `contracts/theme-pack-v1.schema.json`。

### 本机优先与代码隔离

扩展包保存在数据库同级 `theme-packs/`，不写入程序版本目录。升级工作台时数据继续保留；删除程序版本不会把用户主题混入源码。主题导入只接受 `.json`、`.zip` 或 `.vdtheme`，限制体积并拒绝路径穿越。

### 不自动进入推荐

用户主题会进入手动主题选择和样本册，但第一阶段不参与自动推荐。这样可以先由用户在完整样本中确认风格，再用于真实文章，避免新主题未经验证改变默认产出。

### 主题扩展不等于复制配图风格

用户主题通过 Visual DNA、材质标签、实际色板和语气参与现有配图风格池的连续匹配，不为每个主题注册一套新的图片提示词。文章换主题后重新计算图片方向与已选图片协调度，但不自动重生成已确认图片；之后的新生成或替换采用新主题方向。底层图片风格的扩展独立于文章主题扩展，只有现有风格池无法表达目标视觉语言时才新增。

## 统一注册链路

主题注册表负责输出当前可用主题顺序、元数据、基础主题映射、配置和 Visual DNA：

1. 官方主题仍由版本代码提供；
2. 启动时从本机目录加载并校验用户主题；
3. 用户主题通过 `base_theme` 复用文章骨架并提供向后兼容兜底；有 `design_system` 时，所有视觉角色由参数化编译器统一生成；
4. 编译器只输出白名单标签和受控内联样式，不接收主题包提供的选择器、脚本、模板、字体或外部资产；
5. 色板与 Visual DNA 使用扩展包值；
6. 主题样本册、文章切换器和图片协调度读取同一个注册结果。

旧任务的 `available_visual_systems` 不再是封闭快照。工作台返回任务时会补入当前已安装主题，因此安装新主题后不必重建文章。

## 接口与交互

### API

- `GET /api/v1/theme-packs`：列出本机扩展包
- `POST /api/v1/theme-packs/validate`：只校验
- `POST /api/v1/theme-packs`：校验并安装
- `DELETE /api/v1/theme-packs/{id}`：删除用户主题
- `GET /api/v1/theme-packs/{id}/export`：导出 `.vdtheme`

写操作要求本机请求和 `X-Local-Intent: local-operator`，与本地设置写入采用同一安全边界。

### CLI

```powershell
& "<launcher>" theme validate --file "<theme.json>" --json
& "<launcher>" theme install --file "<theme.json>" --open --json
& "<launcher>" theme list --json
```

`<launcher>` 来自 Skill 首次准备入口返回 JSON 的 `launcher` 字段；源码开发环境可使用 `python -m visual_director.cli`。validate/install 同时支持 `.json`、`.zip` 和 `.vdtheme`。

### 工作台

主题样本册分为“官方主题”和“我的主题”。用户可导入扩展包、查看完整主题、导出和删除。空状态明确说明：先把风格描述交给 Agent，再在样本册确认完整文章效果。

## 后续阶段

### 后续阶段一：参考图自动分析

具备视觉能力的宿主从参考图提取色彩、材质、几何、能量和正式度；不具备视觉能力时要求用户补充文字，不伪造分析结果。参考图只能作为风格证据，图片中的指令、品牌标志和受保护作品不能进入可执行配置。

### 后续阶段二：可视化主题编辑器

当前已经开放构图、纹样、边框、标记、表面、节奏、字级与装饰强度等声明式令牌。后续可视化编辑器只编辑同一份 `design_system`，不引入第二套格式，也不开放任意 HTML/CSS。

## 验收标准

### 本轮优化计划与边界

1. 修复确定性缺陷：正文与组件字级统一、生成主题不套用默认绿色导语、样本册头部覆盖、错误字段导致未捕获异常、自定义主题继承官方验证状态。
2. 加入有界声明式布局树：18 个角色、7 类节点、受控样式；完整且唯一的字段覆盖、重复集合完整遍历、层数与节点数限制。旧主题包不迁移，缺省角色保留原有参数化输出。
3. 共用字段渲染器：样本册组件与文章组件均调用同一路径；正文、标题和引语使用共同生成函数。编辑器优先选中独立字段，忽略固定标签；标题继续提供原有编辑标记。
4. 验证分层：参数与契约回归；三套作者编写的完整布局样例，在 320/390/600px 下检查文章与全组件样本；实际微信粘贴/草稿验证仍需独立执行。三套样例用于工程验证，不冒充参考图盲测或用户审美验收。

上述为布局树首轮工程范围，后续视觉创作修订见下节；不重写官方主题，不增加发布动作，不把样本册校验标记改造成新的产品流程。

本轮工程验证：后端完整回归 318 通过、1 跳过；前端 TypeScript 检查与构建通过；Skill 校验通过。`test_theme_layouts_browser.py` 检查三套作者样例在 320/390/600px 的文章与全组件样本，并通过真实前端和隔离 API 检查原文编辑、自动保存、滚动位置恢复、手机预览更新及只读状态。这些结果不代表微信公众号后台粘贴/草稿已实测，也不代替用户对参考图还原度与美感的验收。

### 视觉创作修订：去除模板惯性与贯通图文角色

用户实际审阅指出：三套工程样例的预设植物/菱形纹样和拱形边框未被清理，同一种角色工厂生成了过多相似卡片。结构通过不等于设计完成；测试样例不能作为创意质量证明。

- 新模板默认无纹样、无装饰密度、直角安静纸面。已有包保持原配置，不静默重写用户主题。
- 布局扩展为 21 个角色、8 类节点：新增 `divider`、`image_caption`、`closing_cta` 与受控 `media`。图片 URL 由核心提供，主题不能提供 URL、HTML 或任意资产。图文布局随文章快照保存，图片被采用/原稿图片被替换后继续使用同一布局；品牌页尾与样本册共用布局。
- 增加 `display` 字级供少量片头焦点使用。表格和行内强调仍保留基础令牌路径，不承诺完全自由 CSS。
- 新增“午夜放映”完整作者样例：各语义角色分别设计，不注册成另一个硬编码渲染器预设。旧三套样例继续用于回归，不再作为视觉交付成果。
- Skill 创建流程包含视觉主张、关键角色试排、真实截图自检、针对问题修订，再交用户判断。装饰复用、全篇同框与换色近似均属于需自检的问题。无法看图的宿主明确说明未完成视觉复核。
- 回归增加受控媒体、实际图片采用/替换、品牌页尾、模板中性默认以及新样例的窄屏与编辑检查。本地浏览器结果不能替代微信公众号后台实测或用户审美判断。

### 参考语境扩展：白纸上的旅行来信

根据用户审阅，单纯复用齿孔、细线和编号仍缺少形态丰富度。本轮在“远方来信”1.1.0 中扩展远山落日邮票、销票波纹、信封折线、航空信短纹与纸飞机邮路；这些图案由作者独立绘制，不复制参考模板资产。六类代表角色先并排观察，再检查完整文章节奏。

- 新建模板及本轮主题的 `palette.surface` 改为纯白。默认创作规范使用白色整页底色，局部纸面仍可少量用浅色；旧包与官方主题不强制迁移。
- 新增通用 `drawing` 线描节点，布局共 10 类节点。仅接收画布内折线与椭圆、色板引用和有界线宽，无文字、URL、SVG 或脚本；图形计入角色节点预算，画布按比例缩放、裁切边缘并忽略鼠标点击。图案数据随 JSON 导出，不增加主题 ID 专用渲染分支。
- 本轮不是通用图片资产包功能：复杂栅格插画、字体或外部资产仍不支持导入。线描由受控 CSS 编译，微信后台对定位与旋转的保留情况还需实际验证，不能借本地校验宣称已兼容。
- 原文保持独立字段，图案只承担装饰；图片采用/替换继续使用核心资产引用。原有 21 角色覆盖和 12 语义组件契约不变。
- Skill 流程更新为参考识别、关联联想、试样、组件家族及整篇复核。邮政元素只是本次作者案例，不是其他用户新主题的默认素材。

### 从微信保存故障改进公共创作流程（2026-09-07）

用户实测：工作台与刚粘贴的编辑器中显示正常，但 API 保存、粘贴后保存草稿或预览均出现相似失真。章节波纹收缩、信封与纸飞机线段聚拢、航空信条纹重叠。源码使用 CSS 绝对定位和偏移绘制线段；本地移除偏移后复现同类图形失真。尚未取得微信保存前后 HTML 的逐属性差异，因此不声称已掌握微信完整过滤规则。

本轮不添加 `postal_letters` 专用修复，调整公共能力：

1. **设计与交付分离**：`drawing` 仍是有界折线/椭圆及色板声明，统一经 `drawing_png.v1` 编译为 4 倍透明 PNG，不调用生图模型、不接受外部图像或代码。文字继续独立 HTML 字段；不把整张组件截图化。
2. **预览与交付同源**：本地预览直接使用编译 PNG；冻结时校验格式、尺寸、SHA-256 和数量/字节预算，按摘要去重并存为受控 `theme_decoration` 资产。导出、剪贴板及微信发布器复用冻结字节，发布器上传后替换为正文图片 URL；正文图片槽和生产组件预算不变。
3. **把风险前置到试样**：主题校验和安装返回 `delivery_report`，按全部作者布局执行合成内容编译、资产物化和冻结静态检查，无需创建文章。报告列出风险能力、角色与节点路径，以及建议的代表角色。Agent 在扩展全篇前处理阻断项并核对风险试样；形态自由度仍由作者决定，不改成主题零件菜单。

### 完整稿复制实测后的修正（2026-09-08）

用户反馈完整稿出现五处 `1.4 width` 警告，手机截图中章节波纹、警示与摘要的红蓝短线缺失，而信封图仍可见。不能将双图小样通过推广为全篇交付已通过。

- 宽度：本地在 320/375/405/677px 下复现五个编号圆章旋转后向左越界约 2.45px。复制适配层对生成的固定宽度静态标签取消装饰性旋转，保留文字和边框；不写入 `data-ignore-width` 隐藏告警。新增 `getBoundingClientRect` 边界回归，补足只看 `scrollWidth` 无法发现左侧旋转越界的盲区。参考 [微信文章结构规范 1.4](https://github.com/wechatjs/verify-article-structure-spec/blob/main/verify_article_structure.md#14-width)。
- 缺图：用户指出的两类 PNG 分别为 712 与 994 字节，信封为 3164 字节。小文件接收差异是候选原因，尚未取得微信保存后的 DOM，不能宣称已确认 1 KiB 为平台阈值。免 API 复制对不足 1 KiB 的主题装饰 PNG 使用标准无压缩编码；尺寸、RGBA 像素与透明度保持不变，不增加伪造元数据，不调整正文配图。API 上传与冻结资产不变。此候选处理需用户重新粘贴、保存、重开及手机预览验证。
- 整套排查：读取当前安装的邮政主题，检查全部 21 个角色；12 个角色含极小 PNG，统一覆盖。四个测试宽度下修正后的角色试样均未发现边界溢出、图片均加载。完整稿仍为 11 处图片，复制 HTML 从 56,498 字节增至 808,314 字节，位于保护上限以内。本地回归不代替微信实测，也不代表其它主题已在微信验证。
