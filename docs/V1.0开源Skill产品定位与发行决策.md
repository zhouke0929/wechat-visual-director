# V1.0 开源 Skill 产品定位与发行决策

- 文档状态：D154–D211 已接受
- 产品负责人：徐均舸
- 日期：2026-07-22
- 阶段目标：把现有公众号视觉编译器收口为本地优先、可一行安装、可由 OpenClaw 调用的开源产品

## 1. 产品定义

V1.0 定位为“开源、本地优先的公众号视觉主编 Skill”。运营在 OpenClaw 中输入文章需求，宿主模型按照约定生成结构化初稿；Skill 调用视觉编译器创建任务并打开本地 Web 工作台；运营确认主题、组件、封面和插图后，将成稿同步至微信公众号草稿箱。无法配置公众号接口时，系统提供富文本复制与成稿导出作为降级路径。

Skill 不是单一提示词文件，而是可安装的软件包。建议发行包至少包含：

```text
wechat-visual-director/
├── SKILL.md                 # 触发条件、工作流和宿主模型行为约束
├── scripts/                 # 启动、配置、任务创建和发布脚本
├── app/                     # 视觉编译器、Web 工作台和本地数据
├── templates/               # Markdown 协议、视觉系统与组件资源
├── adapters/                # OpenClaw、图片模型和微信发布适配器
├── references/              # 配置、故障排查与兼容说明
└── manifest/lock files      # 版本、依赖和安装元数据
```

其中 Skill 是宿主 Agent 看得懂并能调用的入口；视觉编译器、Web 工作台和发布适配器是独立、可测试、可复用的核心程序。这一组合统一称为“公众号视觉主编 Skill”。

## 3. 一行安装目标

V1.0 的发行体验目标是让具备 Node.js 环境的用户通过一条命令完成安装和初始化，例如：

```bash
npx wechat-visual-director init
```

或者由 OpenClaw 的 Skill 安装机制从 GitHub 安装：

```bash
openclaw skill install github:<owner>/wechat-visual-director
```

以上命令目前是目标接口，不代表已经发布或可以执行。最终命令需要以 OpenClaw 当前支持的安装规范、包名占用情况和跨平台验证结果为准。

一行命令背后仍会执行多项工作：

1. 检查 Node.js、Python 或已打包运行时；
2. 下载固定版本的 Skill 和核心程序；
3. 创建本地数据目录；
4. 启动配置向导；
5. 安装或注册 OpenClaw Skill；
6. 启动本地 API 与 Web 工作台；
7. 执行健康检查并返回本地访问地址。

因此“一行安装”是发行层对复杂性的封装，不等于项目内部只有一份文本文件。

## 4. 推荐运行模式

### 4.1 OpenClaw 模式（首发）

```text
运营自然语言需求
→ OpenClaw 宿主模型生成规范化 Markdown
→ Skill 创建本地视觉任务
→ 浏览器自动打开工作台
→ 人工确认
→ 微信草稿适配器 / 富文本复制 / 成稿导出
```

宿主模型负责内容生成与结构化输出。视觉编译器继续负责解析、语义纠错、视觉规划、确定性渲染、图片槽、历史避重和质量检查。

### 4.2 独立模式（兼容）

没有 OpenClaw 的用户可以直接启动本地工作台，上传或粘贴 Markdown。独立模式默认使用确定性规划；需要模型增强时由用户自行配置文本模型 Key。

## 5. 配置分级

| 配置 | 是否必需 | 缺失时行为 |
|---|---:|---|
| 本地运行环境 | 是 | 安装器提示并终止，不留下半安装状态 |
| OpenClaw | OpenClaw 模式必需 | 仍可使用独立工作台 |
| 文本模型 Key | 否 | OpenClaw 模式复用宿主模型；独立模式使用规则规划 |
| 图片模型 Key | 否 | 允许上传、沿用原图或跳过配图 |
| 微信 AppID/AppSecret | 否 | 禁用自动草稿，保留复制和导出 |
| 微信接口白名单 | 自动草稿必需 | 配置向导展示检测结果和修复步骤 |

公众号密钥不得写入 `SKILL.md`、模型提示词、对话上下文或前端存储。应保存在本地环境变量、系统凭据存储或不被模型读取的私有配置文件中。

## 6. 开源 MVP 边界

首版必须完成：

- 自然语言需求到规范化初稿的 Skill 工作流；
- 不规范 Markdown 的结构修复与语义保护；
- 本地 Web 排版工作台；
- 多视觉系统、语义组件和最近五篇避重；
- 图片上传，以及可选的 BYOK 生图适配器；
- 本地任务和已确认成稿保存；
- 自动打开工作台；
- 微信草稿、富文本复制和成稿导出三种交付路径；
- 配置向导、健康检查、错误提示和卸载说明；
- Windows 优先的一行安装与从零安装验证。

首版不包含：

- SaaS 用户、团队与权限系统；
- 计费和模型额度转售；
- 云端长期托管；
- 公众号数据看板和 A/B Test；
- 复杂长期记忆、推荐算法和自动偏好学习；
- 多 Agent 平台同时首发。

## 7. 商业化保留边界

开源核心保持本地可用和 BYOK。未来托管版可以围绕无需部署、固定出口 IP、密钥托管、团队品牌资产、多账号协作、稳定发布、模型额度和高级组件收费。核心数据结构、Provider 接口、Publisher 接口和历史存储需要保持可替换，但当前不实现计费逻辑。

## 8. 下一阶段顺序

1. 冻结 OpenClaw Skill 与核心程序的职责边界；
2. 定义自然语言需求到规范化 Markdown/文章结构的输入协议；
3. 将当前 API 与 Web 封装成可由一个启动器管理的本地应用；
4. 实现首次运行配置向导和独立模式；
5. 编写 OpenClaw Skill，打通“创建任务—打开工作台—获得结果”；
6. 接入微信草稿适配器及复制/导出降级路径；
7. 在一台未配置过项目的 Windows 电脑上执行从零安装测试；
8. 清理示例、密钥、许可证和文档后发布 GitHub 仓库。

当前阶段不应先优化 npm 包名、Logo、官网或收费设计。下一项研发工作是第 1、2 步：确定安装后各模块如何协作，以及宿主模型必须输出什么。

### 10.1 当前实现与路线图区分

本文第 1、4、6 节描述的是已接受的 V1.0 产品目标，不代表每项均已在 Alpha 实现。公开 README 和 CLI `doctor` 必须以运行时真实能力为准：

- 已实现：Markdown 预检、规则/可选智能规划、双方案、组件与图片确认、本地任务保存、冻结版本；
- 未实现：真实微信公众号草稿创建、富文本一键复制、最终群发；
- 安全约束：即使未来接入微信发布适配器，最终群发仍需在微信后台由人工确认。

### 10.2 公开仓库门禁

GitHub 首发前必须同时通过：

1. 中性品牌运行验证，页面和新任务不依赖私有资产；
2. 敏感词、密钥模式、二维码和内部样本扫描；
3. 后端测试、前端类型检查/构建、Skill 校验和浏览器主链路回归；
4. `README`、`SKILL.md`、CLI `doctor` 三处能力声明一致；
5. 从 GitHub 克隆后的干净 Windows 环境安装验收。

| D216 | 图片使用全屏大图审核 | 支持缩放、滚动查看、锁定原文对照和模型原始输出，解决小缩略图无法判断的问题 |
| D217 | 合并文字确认与图片采用 | OCR 未证明一致时，“文字无误，采用此图”本身即为人工确认，不再重复勾选 |
| D218 | 图片候选进入连续审核队列 | 采用一张后进入下一张待审核图片，减少页面上下往返 |
| D219 | 工作稿继续自动保存，微信配置就绪时使用单一最终动作 | “保存并创建公众号草稿”一次完成冻结和草稿创建；群发仍必须在公众号后台人工完成 |
| D220 | 下一阶段优先提升组件丰富度与图片质量 | 先用真实长文跑通本地完整链路，再决定公开 Alpha.9 的发行 |

## 17. 四主题系统与组件语义纯净决策（D221–D229）

| 编号 | 决策 | 实现含义 |
|---|---|---|
| D221 | 主题包成为排版的主要视觉单位 | 主题统一约束字体、配色、边界、留白、图片样式和组件形态；不再鼓励跨主题组件混搭 |
| D222 | 组件渲染器不得创造正文语义 | 组件只能呈现原文绑定内容；口号、事实、结论和行动建议不得由模板写死，装饰限于编号、线条、图标和色块 |
| D223 | 先升级现有四套主题，再新增六套 | 轻盈阅读、温暖人文、编辑对比、理性网格先完成主题化评审；通过后再扩展至十套 |
| D224 | 每套主题第一轮覆盖八类核心组件 | 编号观点、概念解释、证据强调、行动清单、前后变化、风险提示、对比卡片和阶段小结必须拥有主题内独立形态 |
| D225 | 低频组件进入第二批扩展 | 问题钩子、案例卡片、FAQ 和复杂逻辑路径不阻塞第一轮主题验收 |
| D226 | 建立主题总览和一主题一页的样本册 | 每页同时提供完整长文和独立组件样张，先评整篇协调性，再评单个组件 |
| D227 | 组件切换只允许在同一主题内微调 | 当前切换入口暂时保留并降级为可选；后续根据运营真实修改率决定是否继续隐藏或删除 |
| D228 | 最近五篇历史升级为主题优先的防重复依据 | 先避免近期主题和组合签名重复，再在同一主题内部选择组件；手动指定主题始终允许覆盖 |
| D229 | 采用小批量主题验收 | 先完成现有四套主题；新增六套按每批两套开发和评审，避免一次性制作后整体返工 |

主题评审阶段允许在任务台临时展示“主题样本册”入口。完成四主题验收并进入日常运营后，再依据使用频率决定是否将其恢复为只通过固定地址访问的研发入口。

## 18. 主题套件构图升级决策（D230–D237）

| 编号 | 决策 | 实现含义 |
|---|---|---|
| D230 | 现有第一批组件降级为兼容草稿 | 已验证的旧变体继续可用，但不再作为最终视觉质量标准 |
| D231 | 组件差异以构图和轮廓衡量 | 换色、换圆角和换边框不计为有效视觉差异 |
| D232 | 同主题统一设计基因而不是统一容器 | 配色、字体、线条、装饰语言和留白保持一致；组件形态必须多样 |
| D233 | 卡片型组件占比不得超过完整文章组件的 35% | 正文承担叙事，组件只用于确有必要的信息关系 |
| D234 | 主题套件纳入非卡片节奏部件 | 每套包含章节标题、小标题、行内强调、图文位置、分割线和 CTA |
| D235 | 第一轮只重做轻盈阅读与理性网格 | 两套方法通过产品与运营评审后，再升级温暖人文和编辑对比 |
| D236 | 样本册同时评审完整文章与主题部件库 | 先看长文节奏，再逐项评审六类节奏部件和八类语义组件 |
| D237 | 只抽象成熟编辑器的视觉语法 | 不复制第三方模板、素材和代码；所有微信 HTML/CSS 由项目原创实现 |

第一轮实现将组件库升级为 `wechat_components.v0.7.0`。轻盈阅读使用开放式标题、叶片线条、漂浮批注和少量柔色块；理性网格使用栏目索引、数据脊柱、坐标轴和非对称账页。

第二轮实现将组件库升级为 `wechat_components.v0.8.0`。温暖人文升级为“成长手札/纸页叙事”主题套件，编辑对比升级为“独立杂志/校样版面”主题套件。至此四套主题均进入 `theme_kit_v1_review`，每套都包含正文节奏部件、8 类核心语义组件和整篇组合样张。

## 19. 主题节奏部件正式链路决策（D238–D244）

| 编号 | 决策 | 实现含义 |
|---|---|---|
| D238 | 主题样本册不得展示生产链路不存在的能力 | 每个节奏部件必须标记正式触发方式，并由自动化测试验证 |
| D239 | `**重点短语**` 是行内强调的唯一作者语义 | 渲染器按主题生成划线、纸带、头条或索引式强调；不要求 Markdown 指定颜色 |
| D240 | `---` 表示真实内容转场 | 解析器保留 thematic break，渲染器按主题生成分割线；不在每个 H2 前后自动插入 |
| D241 | 图片位置和图注分别受控 | 图片位置来自原稿或视觉计划；可靠的原稿图片 alt 可作为低强调图注，模型生成图不自动编造图注 |
| D242 | 图片外框属于主题系统 | 预览占位与发布后真实图片使用同一主题 frame 标识，避免物化图片后退回通用圆角框 |
| D243 | 固定品牌 CTA 内容不随主题改写 | 品牌文案和资产保持配置值，只有外层构图、边线和留白跟随主题 |
| D244 | 来源信息保持统一低强调 | 数据来源不参与主题化重点表达，继续使用小字号、弱色和通用结构 |

该轮将组件库升级为 `wechat_components.v0.9.0`，渲染器升级为 `preview_renderer.v0.12.0-rhythm-contract`。输入 Schema 继续保持 `wechat_article.v1`，宿主只需输出标准 Markdown。
