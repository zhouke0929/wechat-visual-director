# V1.0 开源 Skill 产品定位与发行决策

- 文档状态：D154–D314 已接受并实现
- 产品负责人：徐均舸
- 日期：2026-07-22
- 阶段目标：把现有公众号视觉编译器收口为本地优先、可一行安装、可由 OpenClaw 调用的开源产品

## 1. 产品定义

V1.0 定位为“开源、本地优先的公众号视觉主编 Skill”。运营在 OpenClaw 中输入文章需求，宿主模型按照约定生成结构化初稿；Skill 调用视觉编译器创建任务并打开本地 Web 工作台；运营确认主题、组件、封面和插图后，将成稿同步至微信公众号草稿箱。无法配置公众号接口时，系统提供富文本复制与成稿导出作为降级路径。

Skill 不是单一提示词文件，而是可安装的软件包。建议发行包至少包含：

```text
wechat-visual-director/
├── SKILL.md                 # 触发条件、工作流和宿主模型行为约束
├── scripts/                 # 启动、配置、任务创建和发布脚本
├── app/                     # 视觉编译器、Web 工作台和本地数据
├── templates/               # Markdown 协议、视觉系统与组件资源
├── adapters/                # OpenClaw、图片模型和微信发布适配器
├── references/              # 配置、故障排查与兼容说明
└── manifest/lock files      # 版本、依赖和安装元数据
```

其中 Skill 是宿主 Agent 看得懂并能调用的入口；视觉编译器、Web 工作台和发布适配器是独立、可测试、可复用的核心程序。这一组合统一称为“公众号视觉主编 Skill”。

## 3. 一行安装目标

V1.0 的发行体验目标是让具备 Node.js 环境的用户通过一条命令完成安装和初始化，例如：

```bash
npx wechat-visual-director init
```

或者由 OpenClaw 的 Skill 安装机制从 GitHub 安装：

```bash
openclaw skill install github:<owner>/wechat-visual-director
```

以上命令目前是目标接口，不代表已经发布或可以执行。最终命令需要以 OpenClaw 当前支持的安装规范、包名占用情况和跨平台验证结果为准。

一行命令背后仍会执行多项工作：

1. 检查 Node.js、Python 或已打包运行时；
2. 下载固定版本的 Skill 和核心程序；
3. 创建本地数据目录；
4. 启动配置向导；
5. 安装或注册 OpenClaw Skill；
6. 启动本地 API 与 Web 工作台；
7. 执行健康检查并返回本地访问地址。

因此“一行安装”是发行层对复杂性的封装，不等于项目内部只有一份文本文件。

## 4. 推荐运行模式

### 4.1 OpenClaw 模式（首发）

```text
运营自然语言需求
→ OpenClaw 宿主模型生成规范化 Markdown
→ Skill 创建本地视觉任务
→ 浏览器自动打开工作台
→ 人工确认
→ 微信草稿适配器 / 富文本复制 / 成稿导出
```

宿主模型负责内容生成与结构化输出。视觉编译器继续负责解析、语义纠错、视觉规划、确定性渲染、图片槽、历史避重和质量检查。

### 4.2 独立模式（兼容）

没有 OpenClaw 的用户可以直接启动本地工作台，上传或粘贴 Markdown。独立模式默认使用确定性规划；需要模型增强时由用户自行配置文本模型 Key。

## 5. 配置分级

| 配置 | 是否必需 | 缺失时行为 |
|---|---:|---|
| 本地运行环境 | 是 | 安装器提示并终止，不留下半安装状态 |
| OpenClaw | OpenClaw 模式必需 | 仍可使用独立工作台 |
| 文本模型 Key | 否 | OpenClaw 模式复用宿主模型；独立模式使用规则规划 |
| 图片模型 Key | 否 | 允许上传、沿用原图或跳过配图 |
| 微信 AppID/AppSecret | 否 | 禁用自动草稿，保留复制和导出 |
| 微信接口白名单 | 自动草稿必需 | 配置向导展示检测结果和修复步骤 |

公众号密钥不得写入 `SKILL.md`、模型提示词、对话上下文或前端存储。应保存在本地环境变量、系统凭据存储或不被模型读取的私有配置文件中。

## 6. 开源 MVP 边界

首版必须完成：

- 自然语言需求到规范化初稿的 Skill 工作流；
- 不规范 Markdown 的结构修复与语义保护；
- 本地 Web 排版工作台；
- 多视觉系统、语义组件和最近五篇避重；
- 图片上传，以及可选的 BYOK 生图适配器；
- 本地任务和已确认成稿保存；
- 自动打开工作台；
- 微信草稿、富文本复制和成稿导出三种交付路径；
- 配置向导、健康检查、错误提示和卸载说明；
- Windows 优先的一行安装与从零安装验证。

首版不包含：

- SaaS 用户、团队与权限系统；
- 计费和模型额度转售；
- 云端长期托管；
- 公众号数据看板和 A/B Test；
- 复杂长期记忆、推荐算法和自动偏好学习；
- 多 Agent 平台同时首发。

## 7. 商业化保留边界

开源核心保持本地可用和 BYOK。未来托管版可以围绕无需部署、固定出口 IP、密钥托管、团队品牌资产、多账号协作、稳定发布、模型额度和高级组件收费。核心数据结构、Provider 接口、Publisher 接口和历史存储需要保持可替换，但当前不实现计费逻辑。

## 8. 下一阶段顺序

1. 冻结 OpenClaw Skill 与核心程序的职责边界；
2. 定义自然语言需求到规范化 Markdown/文章结构的输入协议；
3. 将当前 API 与 Web 封装成可由一个启动器管理的本地应用；
4. 实现首次运行配置向导和独立模式；
5. 编写 OpenClaw Skill，打通“创建任务—打开工作台—获得结果”；
6. 接入微信草稿适配器及复制/导出降级路径；
7. 在一台未配置过项目的 Windows 电脑上执行从零安装测试；
8. 清理示例、密钥、许可证和文档后发布 GitHub 仓库。

当前阶段不应先优化 npm 包名、Logo、官网或收费设计。下一项研发工作是第 1、2 步：确定安装后各模块如何协作，以及宿主模型必须输出什么。

## 20. Alpha.10 修复决策与真实文章回归记录

本节记录 Alpha.9 发布后的真实使用问题。以下修复范围已于 2026-07-28 接受，纳入 Alpha.10：

| 决策 | 内容 | 产品理由 |
|---|---|---|
| D245 | 持久安装同时注册通用用户级 Skill 与 OpenCode Skill | 新对话不再依赖临时仓库上下文 |
| D246 | OpenCode 增加显式 `/wechat-visual-director` 命令入口 | 自动触发失败时仍有可发现、可解释的确定入口 |
| D247 | 写稿后执行“事实锁定的语义整理” | 把原文真实的并列、步骤、概念和二维数据显式表达出来 |
| D248 | 长分析稿结构过平时阻断自动规划并返回 `source_structure_too_flat` | 不让用户把“原稿没有可绑定结构”误判为组件库失效 |
| D249 | 规划结果暴露候选结构、最终采用组件和编译调整 | 能区分写稿、Brief 和安全编译三个环节的问题 |
| D250 | 渲染器继续禁止擅自拆段、造表和补结论 | 丰富度提升不能以篡改事实和文章逻辑为代价 |

### 20.1 跨会话 Skill 发现

- 现象：同一台电脑在完成安装的原对话中可以运行 `wechat-visual-director`，重新打开 OpenCode 对话后无法自动发现，斜杠菜单中也不存在该 Skill。
- 已定位原因：当前持久安装器只安装视觉主编核心程序，没有把 Skill 入口同步注册到宿主 Agent 的用户级 Skill 目录；原对话依赖临时仓库上下文，因此换对话后丢失发现能力。
- Alpha.10 修复：安装和升级时注册或刷新用户级 Skill；`doctor` 增加 `host_skill_registered` 检查；补充 OpenCode 命令入口，但核心程序继续保持宿主无关。

### 20.2 真实长文组件覆盖不足

复现输入为“贵港工贸职业学院教育资产流拍—民办高校存量博弈—教育发展‘十五五’规划”分析稿。相同选题下：

- 最新 Skill 生成稿主要由 H2、连续正文、行内强调、引文和两张图片组成，只出现章节标题与证据引文等少量视觉部件；
- 最新稿导语与第一章还重复讲述了同一事件，说明写稿阶段除语义扁平外也缺少结构去重；
- 运营调整稿包含真实数据表、并列因素、编号政策信号、原因拆解和行动建议，组件形态与阅读节奏明显更丰富；
- 文章内容本身存在足够的真实结构，问题不属于“选题不适合组件”。

根因位于内容写作与视觉规划之间的结构契约：

1. 当前 Skill 虽要求规范 Markdown，但“不要为了触发组件制造结构”的约束容易让宿主把真实的并列关系、政策影响和数据对比继续写成普通段落；
2. 视觉编译器只允许组件绑定原文已有的 H3、列表、引文和二维表格，不得擅自把连续正文拆成列表或补造比较关系；
3. 因此即使组件库已经丰富，只要写稿阶段输出为“第一、第二、第三”的连续段落，后续 Brief 和渲染器也只能安全降级为普通排版；
4. 该安全降级原则本身应保留，Alpha.10 应修复的是结构化写稿与可观测性，而不是让渲染器改写事实。

Alpha.10 修复：

- 在宿主写稿流程中增加一次“组件友好但事实锁定”的语义整理：真实并列因素使用列表，真实先后步骤使用有序列表，真实二维数据使用表格，概念使用 H3 与紧随定义段；不得为凑组件补造关系；
- 长分析稿若存在大量正文段落，却没有列表、H3、表格或可绑定证据，预检返回 `source_structure_too_flat`，允许宿主基于原有事实进行一次结构整理；
- 规划结果增加候选数、最终采用数及降级原因，区分“原稿没有候选”与“Brief 选择后被安全降级”；
- 本节复现提示词已固化为 `samples/evaluation/realistic/alpha10-private-college-stock-game-regression.json`，后续必须在不依赖旧窗口记忆的新对话中执行。

验收标准：

1. 新对话能够直接发现并调用已安装 Skill；
2. 复现文章至少形成三种有事实依据的结构角色，例如事件证据、行业数据/对比、政策影响或读者行动建议；
3. 不把 H1/H2 吞入组件，不改写数字与来源，不为了视觉效果制造表格、结论或行动建议；
4. 若结构仍不足，系统明确提示原因，而不是让用户误以为组件库失效；
5. 同一复现稿继续通过微信草稿兼容性检查，并保持移动端阅读节奏不过度堆砌。

## 23. 未来科技第二版视觉语法决策（D263–D268）

人工横向评审确认“青春校园”比“未来科技”更有设计感。问题不在未来科技的色彩，而在其大量使用圆角舱、胶囊节点和渐变卡片，导致整篇更像 SaaS 界面而不是公众号编辑设计。因此冻结已通过的青春校园，仅重构未来科技。

| 决策 | 内容 | 产品理由 |
|---|---|---|
| D263 | 青春校园冻结为当前基线 | 已获得用户明确偏好，后续修改不得顺带改变其文章骨架与组件样式 |
| D264 | 未来科技改用 `FUTURE FIELD NOTES` 视觉语法 | 以未来实验档案为记忆点，替代抽象的悬浮软件面板 |

| D268 | 主题重构不改变 `wechat_article.v1` 与事实锁定规则 | 本轮只改确定性渲染器，宿主智能体、组件绑定和微信发布链路无需重新配置 |

## 24. 未来科技第三版“未来科学杂志”决策（D269–D274）

第二版虽然摆脱了 SaaS 圆角面板，但人工评审认为密集蓝色线框、重复英文索引和实验记录语法过强，整体更像工程蓝图，仍不具备公众号文章所需的舒适度与吸引力。本轮继续保留主题辨识度，但把“技术说明书”改为“未来科学杂志”。

| 决策 | 内容 | 产品理由 |
|---|---|---|
| D269 | 未来科技采用 `FUTURE EDITION` 视觉语法 | 用科学杂志的版式气质表达未来感，不再依赖工程制图隐喻 |
| D270 | 以极光色带、错位留白和杂志式大字号建立记忆点 | 未来感来自构图、节奏与色彩氛围，而不是密集线框和技术术语 |
| D271 | 组件提示词优先使用中文语义标签 | “关键问题、证据摘录、进程路径、要点回收”等标签比重复英文编号更符合公众号阅读场景 |
| D272 | 软色块只服务于关键信息，不把每段正文装进圆角卡片 | 在丰富度与长文呼吸感之间保持平衡，避免退回 SaaS 卡片堆叠 |
| D273 | 编号继续根据真实条目动态生成 | 大字号索引可以作为杂志节奏，但不得硬编码步骤数量或替代文章原有层级 |
| D274 | Schema、宿主规划和发布链路保持不变 | 本轮仍是确定性渲染器升级，已安装 Skill 无需改变输入协议或重新配置模型 |

组件库版本保持 `wechat_components.v0.11.0`，渲染器升级为 `preview_renderer.v0.16.0-future-science-editorial`。

## 25. Alpha.11 发布与真实运营观察决策（D275–D280）

六套主题已完成人工评审。下一阶段不继续通过增加模板数量追求表面丰富度，而是把当前能力交给真实运营文章验证，识别问题究竟来自组件供给、原稿结构还是 Agent 选择策略。

| 决策 | 内容 | 产品理由 |
|---|---|---|
| D275 | 当前六套主题进入 Alpha.11 发布基线 | 轻盈阅读、温暖人文、编辑对比、理性网格、青春校园和未来科技均已完成人工评审 |
| D276 | 暂缓扩展到十套主题 | 当前 12 类语义组件已经具备基础供给，继续增加主题不能替代真实采用验证 |
| D277 | 下一阶段观察 3–5 篇真实运营文章 | 用自然选题覆盖长短文章、不同结构和不同模型能力，避免继续只在实验稿中优化 |
| D278 | 保留组件切换，但默认方案必须以直接发布为目标 | 手动切换是安全兜底，不应成为每篇文章的固定必经步骤 |
| D279 | 记录自动方案与运营最终方案之间的修改差异 | 修改位置和原因比单纯“满意/不满意”更能定位产品问题 |
| D280 | 完成真实样本后，再决定优化组件、结构识别或选择策略 | 三类问题的根因和解决方式不同，后续迭代必须由证据驱动 |

真实运营观察只记录最小必要信息：选题/文章类型、系统推荐主题、最终使用主题、自动采用组件数、人工修改位置、从生成到草稿的处理时间、草稿创建是否成功和关键截图。文章正文、公众号密钥及内部品牌资产不进入公开仓库。

## 26. Seedream 5.0 信息图与封面无损适配决策（D281–D286）

Alpha.11 真实链路诊断包证明，正文信息图的缺边已经存在于 Seedream 5.0 Lite 原始输出，正文候选的原始文件与系统保存文件字节一致；封面复用则确实由本地 16:9 到 5:4 的中心裁剪造成信息损失。本轮据此拆分模型构图与本地适配问题：

| 决策 | 内容 | 产品理由 |
|---|---|---|
| D281 | 不把 Seedream 4.0 的字数建议当作 5.0 硬限制 | 5.0 官方建议简洁准确，但复杂信息图仍需要明确内容、版式与风格；应删除重复描述而不是机械截断锁定原文 |
| D282 | 结构信息图使用中央安全区与纵向编辑序列 | 左右各留 12%、上下各留 10%；3–4 个长中文节点禁止横向多栏，避免模型把文字和标题画出画布 |
| D283 | 提示词不得向模型暴露系统字段标签 | 不再使用“节点1/节点2”等词，锁定内容改为自然编号，减少系统词被模型误画进成图 |
| D284 | 信息图背景改为冷白基底，暖色只作局部点缀 | 去除大面积米黄/黄色底偏置，并用开放式分区、细线、手绘标记和边缘插画增强轻盈感 |
| D285 | 正文图片缩略图完整显示，封面复用改为无损适配 | 候选缩略图使用 `contain`；16:9 正文图转 5:4 封面时完整保留原图，以柔化背景填充空余区域，不再中心裁切 |
| D286 | Windows 启动器支持 `pnpm.ps1` | 部分电脑只有 PowerShell shim，CLI 应通过 PowerShell 安全启动工作台，不再要求人工执行 `pnpm.ps1 dev` |

图片提示词版本升级为 `v5-seedream-safe-infographic`。本轮只修改新生成候选，不回写已经冻结或已经创建公众号草稿的历史任务。

## 27. 真实长文组件节奏修复决策（D287–D294）

任务 `cc483b38-5de2-459c-a577-0efddc5b68d5` 的诊断结果表明，主题样本册与真实文章之间的视觉差距并非组件库不足：宿主原本建议了概念解释、相邻段落对比和八项行动清单，但兼容层将三者全部降级；随后覆盖兜底又补入重复的编号观点和警示卡，最终五个组件只有三种形态。

| 决策 | 内容 | 产品理由 |
|---|---|---|
| D287 | 真实稿评测同时检查组件数量、形态多样性与文章分布 | “有五个组件”不能代表视觉节奏合格，重复形态仍会产生模板感 |
| D288 | 概念解释继续禁止消费 H1/H2，但允许短 H3–H6 名词标题与紧随解释段 | “院校专业组”这类中文概念不一定出现“是指/定义为”，不应被机械关键词误杀 |
| D289 | 对比卡允许绑定两段相邻且具有明确成对信号的原文段落 | 支持“盲目勾选/完全不勾选”等真实对照，同时禁止拼接不相邻内容或创造结论 |
| D290 | 行动清单允许标题与列表之间存在引导段，并完整支持 2–10 项 | 公众号长清单常有承上启下段；消费列表后必须渲染全部条目，不能静默丢失第 7、8 项 |
| D291 | 45 个以上内容块的超长文章允许 6 个强组件 | 该密度约为每 8–10 块一个视觉入口，仍低于堆砌阈值；其他中长文章继续保持 3–5 个 |
| D292 | 中长文章目标至少四种组件形态 | 补位优先引入未使用的语义组件，而不是继续重复警示卡或编号列表 |
| D293 | 补位优先覆盖文章尚未出现强组件的前、中、后三段 | 避免视觉重点集中在开头或结尾，使长文滚动节奏更均匀 |
| D294 | 多列数据表继续由主题表格渲染，不强制转换成双栏对比卡 | 表格转换会丢失行列事实；视觉丰富不能以信息损失为代价 |

## 32. 单稿主题工作台与冻结历史决策（D320–D331）

真实运营已经能够直接采用自动组件结构，但双方案比较和逐组件换型几乎没有被使用；与此同时，主题历史仅在微信草稿成功后写入，导致复制交付、结果未知和仅冻结的文章无法参与最近五篇避重。本轮据此收敛主工作流：

| 决策 | 内容 | 产品理由 |
|---|---|---|
| D320 | 新任务只生成一份最佳推荐稿并自动选中 | 减少首次理解成本，把运营注意力放在完整文章而不是方案比较 |
| D321 | “换一个主题”由本地确定性核心即时完成 | 复用同一语义结构、图片槽和正文，只替换主题 token 与主题内组件变体，不重新调用 Agent 或图片模型 |
| D322 | 六套主题始终允许人工指定 | 文章类型只参与推荐排序，不得锁死主题；运营判断可以覆盖系统推荐 |
| D323 | 主题切换写入工作稿修订并支持上一版回退 | 用户可以低成本试错，回退必须恢复完整主题而不是在两个状态间重复撤回 |
| D324 | 日常工作台移除逐组件换型面板 | 每个组件的视觉形态归属于当前主题，避免跨主题拼装和冗余操作 |
| D325 | 底层语义组件库继续保留 | 内容结构仍由步骤、证据、概念、对比等组件承载；移除的是运营选型 UI，不是组件能力 |
| D326 | 组件兼容降级接口保留为内部安全能力 | 旧任务、自动化回归和异常降级仍可使用朴素变体，但不在日常工作台暴露组件商城 |
| D327 | 最近主题先避开上一篇，再比较最近五篇使用次数 | 连续主题比总次数更容易产生疲劳；文章适配度只在新鲜度之后作为次级排序 |
| D328 | 最终冻结即写入轻量视觉历史 | 冻结代表运营已经确认视觉稿，不再依赖微信 API 是否成功、复制还是交付包路径 |
| D329 | 同一任务再次冻结时更新原历史，不重复计数 | 继续编辑和重新冻结只代表最终选择发生变化，不应制造多篇虚假历史 |
| D330 | 删除任务保留轻量视觉历史 | 清理正文、图片和任务数据不应抹掉近期已经采用过的主题；视觉历史不保存正文和图片 |
| D331 | 启动时从已有冻结版本回填缺失历史 | 修复旧版本只在草稿成功后记录造成的断层，让现有运营数据立即参与避重 |

主题推荐顺序由本地核心计算：优先避开上一篇主题，再选择最近五篇使用次数更少的主题，最后参考文章类型的视觉适配度。工作台展示最近五篇计数和六主题选择器；切换主题目标为本地一秒内完成，且不得清空已确认图片或改变组件锚点。

## 33. 封面保底与 Seedream 专项生图决策（D332–D339）

真实流程中可能既没有正文配图，也没有用户可上传的封面；同时 Seedream 实测出现氛围图场景雷同、长提示词没有带来更好构图的问题。本轮把“永远可交付”与“供应商专项优化”拆开处理：

| 决策 | 内容 | 产品理由 |
|---|---|---|
| D332 | 封面的“跳过”定义为跳过 AI 与人工上传，而不是生成无封面稿 | 当前 Wenyan 与公众号草稿交付要求封面，真正的空封面会把问题推迟到发布环节 |
| D333 | 一键生成并自动采用本地主题保底封面 | 不消耗模型额度、不要求用户准备图片，同时保持 1080×864 受控资产契约 |
| D334 | 保底封面随六套视觉主题变化，但不生成文字 | 兜底图需要与正文协调，也必须避免模型文字、二维码和品牌误植风险 |
| D335 | 上层继续保存供应商无关的视觉意图，提示词只在 Provider Adapter 边界编译 | 后续切换 Nano Banana 或 GPT Image 不需要重写文章分析和图片槽规划 |
| D336 | Seedream 使用简洁、连贯、用途明确的自然语言提示词 | 依据官方指南，主体/关系/环境优先，随后补充风格、构图、光线与配色，避免堆砌重复修饰词 |
| D337 | 氛围图根据文章类型、语义线索和候选序号确定性轮换场景、构图与媒介 | 不靠随机失控来制造差异，同时解决多张图都像同一张“白底编辑插画”的问题 |
| D338 | 结构信息图继续锁定原文，并保留安全区、移动端字号和人工确认约束 | 提示词变短不能牺牲信息准确性与防裁切要求 |
| D339 | Nano Banana 与 GPT Image 先复用统一视觉意图，不直接照搬 Seedream 提示词 | 三类模型的提示词理解和接口能力不同，需分别通过真实样本探针后再建立专项编译器 |

## 34. 展示型主题样本册与可调封面裁切决策（D340–D346）

工作台实测暴露出三类“内部实现泄漏到用户界面”的问题：配图数量与封面状态被误放在步骤编号位置；已经验收通过的主题仍展示逐项评审与 JSON 导出；封面虽然显示裁切安全框，却不能由运营调整视觉焦点。本轮统一改成正式产品交互：

| 决策 | 内容 | 产品理由 |
|---|---|---|
| D340 | 配图审核与文章封面固定显示流程序号 01、02 | 图片槽数量和封面选择状态不是步骤编号，不能混用同一视觉位置 |
| D341 | 主题样本册从评审工具升级为持续扩充的展示库 | 已通过主题面向用户展示整篇效果与全部部件，不再暴露开发阶段决策控件 |
| D342 | 下线主题逐项通过/修改/淘汰、本地评审状态和 JSON 导出 | 这些能力属于内部设计评审，不属于运营日常使用路径 |
| D343 | 封面完整展示原图，使用可移动的 5:4 裁切框选择保留区域；滑条与鼠标滚轮均支持 1–3 倍缩放并可一键重置 | 让用户直接拖动“最终保留区域”到画面边缘，比移动被遮挡的底图更符合裁切心智 |
| D344 | 裁切保存为新的受控候选并自动采用，不覆盖来源候选 | 保留回退能力，也让发布资产具备明确来源链 |
| D345 | 前后端共同保存缩放比例和横纵偏移，由后端确定性输出 1080×864 PNG | 浏览器预览与最终微信封面必须使用同一组可复现参数 |
| D346 | 移动端裁切器改为单列布局，保留拖动、缩放与保存能力 | 本地工作台主要面向桌面，但不能让窄窗口失去关键交付能力 |

## 36. 插画型信息图视觉脚本决策（D355–D362）

真实 Seedream 样本证明，仅有“信息关系 + 风格词”不足以得到绘本式信息图；当模型还要逐字排入多条长句时，会优先生成规则卡片以降低文字错误。本轮将事实审计与画面表达拆开：

| 决策 | 内容 | 产品理由 |
|---|---|---|
| D355 | `image_visual_intent.v3` 增加供应商无关的 `visual_grammar` | 把场景隐喻、空间区域、节点视觉、连接语言和装饰语法结构化，避免 Provider 只收到一句抽象版式说明 |
| D356 | 长原文默认不整段绘入图片，只使用逐字来自原文的短标签 | 降低中文排版负担，让模型把能力用于视觉叙事而不是长句卡片 |
| D357 | `fact_anchors` 继续完整保存，短标签必须是对应事实锚点的连续原文子串 | 视觉简化不能变成摘要改写，仍可追溯到文章来源 |
| D358 | 短原文节点允许 `verbatim_full_copy`，长节点使用 `label_only` | 简短步骤无需机械截断，复杂正文则优先保证移动端可读性和插画空间 |
| D359 | OCR 核对对象与模型实际绘制文案一致；确定性保底图继续复制完整原文 | 避免用未要求模型绘制的长句误判图片失败，同时保持兜底信息完整 |
| D360 | 节点图形只能使用象征性物体和空间关系，不得把图标当成新增事实 | 插画可以解释关系，但不能虚构院校、数据、政策结论或官方背书 |
| D361 | Seedream 与通用 Images API 分别编译 V3 Prompt，但共享同一视觉脚本 | 保留跨模型可比性，也允许后续针对 Nano Banana、GPT Image 单独优化语法 |
| D362 | 本轮不扩充布局数量，先以相同正文对比旧 Prompt、V3 Seedream 和 V3 Nano | 先验证图片采纳率是否提升，再决定是继续优化编译器还是更换模型 |

## 37. 可逆主题与图片美术方向协同决策（D363–D374）

真实评审发现，图片生成后仍可能需要整篇换主题；如果强制锁定主题，用户会失去低成本试错能力，如果换主题时自动重生图片，又会丢失已确认成果并产生不可预期费用。本轮将文章主题、图片候选和未来生成方向拆成三个可逆状态：

| 决策 | 内容 | 产品理由 |
|---|---|---|
| D363 | 图片生成和采用都不锁定文章主题 | 运营始终可以即时换主题或回退，不因已花费的生图成本进入死流程 |
| D364 | 换主题保留全部已生成、已采用和人工上传的图片候选 | 主题切换只重渲染文章；不得自动删除、覆盖或重生成图片 |
| D365 | 每张新候选保存生成时的主题、美术风格、配色家族、纸面处理和方案修订快照 | 后续兼容判断必须可解释、可复现，不能只靠“看起来像” |
| D366 | 图片与新主题的兼容度由本地确定性规则计算，不调用多模态模型 | 降低延迟、费用和判断漂移，也允许离线工作台完成主题切换 |
| D367 | 一套主题允许多个兼容图片风格，而非主题与图片一一绑定 | 轻盈阅读可容纳扁平插画和纸艺，青春校园也可容纳纸艺和柔和手绘，避免新的同质化 |
| D368 | 完全兼容时静默保留，部分兼容时轻提示，明显不兼容时提供保留、按新主题重生和回退主题三条路径 | 兼容提示服务决策，但不应把每次换主题变成强制确认流程 |
| D369 | “保持当前图片”是默认动作，只有用户显式点击才重新调用模型 | 默认不阻断冻结，也不自动扣费；操作成本与费用归因清楚 |
| D370 | 尚未生成的图片槽和后续新增候选使用当前主题编译美术方向 | 文章决定画什么和信息关系，当前主题决定推荐画材、配色与表面语言 |
| D371 | 同一主题下最多保留三张模型候选；换到新主题后可再生成该主题的候选，旧候选继续保留 | 控制单次试错成本，同时不让历史候选占满新主题的生成空间 |
| D372 | 结构信息图标题移除“第二层、第三步、PART 01”等结构脚手架，只保留原文语义后缀 | 结构编号是规划元数据，不应成为面向读者的图片标题；后缀仍逐字来自原文 |
| D373 | 插画型信息图核心内容占画布 70%–85%，标题区不超过 12%，上下空白带各不超过 8% | 安全区用于防裁切，不能退化成大面积空白；节点应是小场景而不是一排微小图标 |
| D374 | 场景隐喻、连接词和装饰说明全部“只画不写”，渲染文字严格限制为标题和锁定短标签；纸艺风格提供毛边、错位撕纸和装订纸三种同族变化 | 防止模型把 Prompt 说明误画成新事实，同时保留用户认可的纸张质感并减少候选同构 |

兼容提示不改变交付门禁：即使系统判定为明显不兼容，用户仍可保留当前图片并冻结；系统只记录快照和人工选择，不替代运营审美判断。

## 38. 可扩展 Visual DNA 与近期视觉签名决策（D375–D382）

六套文章主题与三类图片风格已经足以验证方向，但继续用“主题 A 兼容图片风格 X/Y”的成对清单扩展，会让每次新增主题或图片风格都必须回改旧配置。真实评审同时表明，大多数跨主题图片并不存在肉眼可见的严重冲突，因此兼容判断应从显式矩阵升级为低干扰的推荐系统：

| 决策 | 内容 | 产品理由 |
|---|---|---|
| D375 | 移除文章主题与图片风格的成对兼容矩阵 | 避免主题数与图片风格数相乘形成持续膨胀的维护成本 |
| D376 | 文章主题与图片风格分别声明统一 Visual DNA | 以温度、饱和度、对比度、几何感、触感、空间维度、视觉能量、信息密度和品牌正式度计算协调度 |
| D377 | 一篇文章只解析一份文章级图片美术方向 | 全部图片槽共享画材、配色、表面语言和气质；各槽只按内容关系改变场景、节点与构图，避免同篇图片各说各话 |
| D378 | 最近五篇冻结稿保存轻量视觉签名 | 在文章主题之外记录图片风格、色板变体、构图家族、表面处理、边缘处理和场景家族，用于真实的视觉新鲜度判断 |
| D379 | 兼容度降为内部推荐分，只有明显冲突才轻提示 | 完全或部分协调时默认静默保留；不增加无意义确认，不阻断冻结，也不自动产生生图费用 |
| D380 | 新主题或新图片风格只注册自己的 Manifest | 新增能力无需修改任何旧主题与旧风格定义，保持扩展边界稳定 |
| D381 | 品牌约束作为稳定外层，差异在品牌边界内产生 | 账号识别、禁用项和事实安全始终固定；画材、构图、色板与场景在允许范围内轮换 |
| D382 | 先迁移现有六主题与三图片风格，再扩充数量 | 无历史时保持现有主要风格倾向；通过旧任务、真实文章和主题切换回归后再新增主题或图片风格 |

文章级图片方向采用可解释评分：内容/图片作用适配 35%，主题 Visual DNA 适配 30%，最近五篇新鲜度 25%，Provider 稳定性 10%。评分只用于确定新生成图片的美术方向；已经生成、采用或人工上传的图片继续保留，用户仍拥有最终审美判断权。

## 39. 未来科技视觉重构与图片加载韧性（D383–D388）

真实评审暴露了两个独立问题：未来科技候选容易退化成“深色道路 + 四块路牌 + 塑料微缩模型”，而连续切换主题时前端偶尔会短暂显示空图。对候选资源连续探测均返回完整文件，因此二者分别按美术方向缺陷和前端加载韧性缺陷处理，不把网络显示问题误归因为图片资产丢失。

| 决策 | 内容 | 产品理由 |
|---|---|---|
| D383 | 未来科技新增独立 `editorial_tech_collage` 图片风格，不再复用理性网格的 `clean_3d_geometry` | 避免未来科技只是理性网格换色，也消除微缩路牌和玩具模型感 |
| D384 | 科技编辑拼贴使用半透明信息薄片、连续信号曲线、纸张纤维和克制 2.5D；禁止路牌、站牌、四块等宽图标、深色道路横贯画面，并限制顶部连续空白 | 让主体和叙事动线占据主要画布，形成有编辑感而非模板化流程图的科技视觉 |
| D385 | 候选缩略图首次加载失败自动重试一次，仍失败时提供原位点击重试 | 短暂网络抖动不应让用户误以为图片丢失，也不应触发生图费用 |
| D386 | 文章预览展示明确的加载、失败和手动重新加载状态，并检查 iframe 内部图片是否真实完成 | 避免工作台只留下空白画面而没有反馈 |
| D387 | 图片与封面工作区请求使用最新请求令牌，旧主题的迟到响应直接丢弃 | 快速连续切换时不得由旧响应覆盖当前主题的候选状态 |
| D388 | 加载重试只重新请求本地图片或预览文档，不删除候选、不更改采用状态、不调用图片模型 | 把显示恢复与内容生成彻底分离，保证成本和用户成果可控 |

## 40. 封面 Visual DNA 与历史任务分页（D389–D394）

真实工作台继续扩展后暴露了两个可持续性问题：封面虽然沿用了文章色板，但 Seedream 场景模板仍可能覆盖当前主题的画材语言；历史任务全部一次加载和展示，任务增长后会让首页持续变长。本轮将两者分别收敛为封面编译规则和服务端分页能力。

| 决策 | 内容 | 产品理由 |
|---|---|---|
| D389 | AI 封面直接复用已经确认的全文 EditorialBrief，不新增第二次文本模型调用 | 标题、整篇叙事和读者任务已经足以确定封面概念，避免额外费用和摘要漂移 |
| D390 | 封面与正文图片共享文章级 Visual DNA，但采用封面专用单焦点构图 | 画材、色板、表面语言和气质保持一致，同时避免把正文信息图直接缩成封面 |
| D391 | Seedream 封面显式编译纸艺、柔和插画、干净 3D 与科技编辑拼贴，并写入对应禁用项 | 防止供应商场景模板把未来科技再次生成路牌、玩具或深色道路 |
| D392 | 封面固定为图片底图、5:4、安全区和单一视觉隐喻，不生成标题、多面板或步骤卡 | 公众号标题由后台承载，底图优先保证移动端识别与后续裁切空间 |
| D393 | 历史任务采用服务端分页，首页默认每页 8 篇，并保留无参数全量列表兼容旧客户端 | 控制页面长度和数据读取量，不破坏已经安装的旧 Agent 调用 |
| D394 | 批量选择限定当前页；翻页清空选择，删除本页最后一项后自动回到仍有内容的上一页 | 避免不可见的跨页误删，并消除删除后出现空页的边界问题 |

## 41. 六套跨行业候选主题与可扩展组件语法（D395–D404）

现有六套主题已经证明工作台可以稳定完成真实公众号交付，但继续只围绕教育行业扩展，容易让新主题退化成旧主题换色。本轮把主题定义从“适合哪个行业”升级为“承担什么表达任务”，在不影响已发布版本和运营生产环境的前提下，建立六套本地候选主题。

| 决策 | 内容 | 产品理由 |
|---|---|---|
| D395 | 新主题按表达任务与阅读情绪分类，不按教育、商业、科技等行业分类 | 同一主题可服务多个行业，避免主题数量随着行业数量线性膨胀 |
| D396 | 本轮候选固定为新中式雅集、复古报刊、波普海报、自然图鉴、商业画报、电影叙事六套 | 分别覆盖文化沉静、新闻纪实、活动冲击、自然观察、商业分析和故事推进六类明显不同的阅读任务 |
| D397 | 六套主题以 `candidate_theme_lab` 状态进入本地主题样册，不直接进入 GitHub Release | 先由产品负责人统一审美验收，再交运营复核，避免未打磨主题影响生产推荐 |
| D398 | 每套候选主题独立注册 Visual DNA、色板、表面材质、构图语法和语气 Manifest | 新增主题无需修改旧主题与图片风格的成对兼容矩阵，延续 D375–D382 的可扩展边界 |
| D399 | 新主题通过“主题语法生成器 + 语义组件载荷”实现，不为每个组件复制一套完整分支 | 组件数量增长时只扩展语法和载荷类型，控制代码体积与回归范围 |
| D400 | 每套候选主题必须覆盖全部核心语义组件，并同时具备标题、强调、引用、列表、表格、图片框、分割线、封面头图和页尾节奏 | 主题不是一张展示皮肤，必须能完整支撑真实长文 |
| D401 | 六套候选必须在版式骨架、留白方式、边框语言、编号形态和阅读节奏上存在结构差异，不接受仅换色 | 用户和运营已经多次确认“换汤不换药”不能解决同质化 |
| D402 | 六套主题共用同一篇长文样本和同一组组件语义进行主题样册验收 | 固定内容变量后才能判断视觉差异来自主题本身，而不是文章结构差异 |
| D403 | 候选主题依次经过产品审美验收、移动端溢出回归、运营复核后才能升级为正式推荐主题 | 将主观审美判断与工程兼容门禁都纳入晋级条件 |
| D404 | 最近五篇主题计数、自动推荐、人工切换和图片 Visual DNA 对全部十二套主题使用同一注册表 | 保留已有历史数据与生产行为，同时避免为新增主题维护第二套逻辑 |

## 42. 候选主题差异化重构与推荐准入（D405–D411）

第一轮审美评审确认：波普海报形成了独立表达，但新中式雅集、复古报刊、自然图鉴、商业画报和电影叙事仍残留“旧组件骨架换色”的问题。主题差异不能只看色板与圆角，而应体现在读者实际感受到的阅读动作上。

| 决策 | 内容 | 产品理由 |
|---|---|---|
| D405 | 主题差异验收从“颜色与装饰不同”升级为“阅读动作不同” | 新中式应像翻阅册页，报刊应像阅读剪报，图鉴应像查阅野外笔记，商业画报应像浏览年度报告，电影叙事应像推进分镜；仅换色一律不通过 |
| D406 | 五套未通过主题重做标题、语义组件、表格、图片框、分隔线与封面头图；已通过的波普海报保持现状 | 避免局部改造后仍被通用矩形卡片和同一种页面节奏拉回旧模板 |
| D407 | 主题样册与人工换主题继续展示全部候选主题，但自动推荐只使用已通过准入的主题 | “可预览”不等于“可进入运营生产稿”，候选研发不能污染真实交付 |
| D408 | 当前自动推荐集合为原六套正式主题加已通过产品评审的波普海报 | 让新增主题逐套晋级，而不是整批主题一起冒险上线 |
| D409 | 自动推荐继续以最近五篇使用次数和避免紧邻重复为第一优先级 | 同质化控制比一次性的文章类型判断更重要，且冻结文章历史仍是唯一可信生产依据 |
| D410 | 在使用次数相同时，增加表格、列表、引文、来源、章节数和段落密度等结构信号 | 文章类型只提供粗粒度语义；真实结构信号能区分数据稿、步骤稿、材料稿和叙事稿，减少模型分类对主题的锁死 |
| D411 | 候选主题须完成产品审美、桌面与 390px 移动端回归、真实文章评审后才能加入自动推荐集合 | 将视觉质量、微信兼容和运营可用性同时作为晋级条件 |

## 43. 非规则装饰与候选主题第二轮重构（D412–D418）

第二轮产品评审指出：仅靠边框、底色和规则矩形，即使细节不同，整篇长文仍会产生“同一套卡片换皮”的整体观感。本轮不复制第三方编辑器模板，而是将成熟模板中可复用的构图规律抽象为自主生成、可随发布资产一同上传的透明装饰素材。

| 决策 | 内容 | 产品理由 |
|---|---|---|
| D412 | 候选主题允许使用项目自主生成的透明 PNG 贴纸、枝叶、胶带、票根、轨道和信号装饰 | 突破只有方框、圆角和底色的形态上限，同时保持素材版权与版本可控 |
| D413 | 贴纸必须由确定性脚本生成并纳入公众号发布资产链，不引用第三方编辑器的专有模板、图片或代码 | 保证开源合规、离线可复现，并避免“本地预览有装饰、微信草稿丢装饰” |
| D414 | 装饰按语义组件限量出现，不在每个模块重复同一贴纸 | 装饰负责建立节奏，不负责填满页面；长文中重复频率过高会制造新的同质化 |
| D415 | 商业画报从年度报告栏线改为“信号轨道 + 轨道圆点 + 不对称气泡”的现代数据画报语法 | 与编辑对比的左右栏、矩形边框和深色顶条形成结构差异，而不只是换色 |
| D416 | 电影叙事改为浅色电影节节目册，使用票根虚线、镜头标记和暖色聚光装饰，取消大面积黑色胶片带 | 保留叙事推进感，同时改善移动端压迫感和日常公众号可用性 |
| D417 | 波普海报保留已通过方向，仅统一进入贴纸资产与发布兼容机制 | 不因整批返工破坏已获得肯定的主题，但补齐工程交付能力 |
| D418 | 旧六套正式主题是否引入非规则装饰，推迟到本批候选完成产品与运营评审后决定 | 先验证新构图规律是否真实提升发布意愿，再避免一次性扩大回归范围 |

## 44. 装饰贴合与电影叙事二次重构（D419–D423）

产品评审确认贴纸方向有效，但暴露出两个新问题：透明图片仍参与普通文档流，会放大模块上方留白；电影叙事虽然换成浅色，却仍由相似卡片反复排列，电影感主要来自英文标签而不是构图。

| 决策 | 内容 | 产品理由 |
|---|---|---|
| D419 | 所有装饰贴纸改用零高度叠放层，组件自身继续负责正常段落间距 | 透明画布不再撑开文章，贴纸与模块形成真实贴合关系，减少段落剥离感 |
| D420 | 禁止“装饰容器间距 + 组件间距”双重叠加 | 主题丰富度不能以牺牲长文阅读连续性为代价 |
| D421 | 电影叙事新增场记板与胶片卷两类自有透明资产，替换抽象票根反复出现 | 让电影识别来自明确视觉母题，而不是依赖 `SCENE`、`CUT TO` 等文字标签 |
| D422 | 电影组件分别采用场记章节、镜头清单、角色档案、剧本提示、正反打、字幕引文和票孔转场 | 每种语义组件承担不同的叙事动作，避免整篇仍是同一米色矩形卡片 |
| D423 | 电影主题继续保持浅色电影节气质，不恢复大面积黑色胶片带 | 同时满足电影辨识度、移动端轻盈感和公众号日常发布适用性 |
| D424 | 商业画报取消“装饰占左列、正文占右列”的并排包装；编号组件使用自身圆点，其他装饰改为零高度边缘叠放 | 装饰列与组件等高会制造不可见占位和双重间距，破坏长文连续性 |

## 45. 新主题图片 Visual DNA 对齐（D425–D430）

六套候选主题的文章排版经过多轮审美重构后，图片 Manifest 仍停留在第一版定义：商业画报仍偏深色年度报告，电影叙事仍偏黑金电影胶片；同时四种通用图片风格不足以表达剪报、图鉴、册页和电影节画册等新增视觉语言。本轮继续坚持 D375–D380 的动态评分架构，不建立主题与图片风格成对矩阵。

| 决策 | 内容 | 产品理由 |
|---|---|---|
| D425 | 六套新主题继续通过统一九维 Visual DNA 与独立图片能力动态评分，不增加 `compatible_styles` 或主题绑定表 | 保持主题数与图片能力数解耦，避免未来扩展成本再次按乘法增长 |
| D426 | 商业画报 Manifest 更新为海军蓝、青柠绿、珊瑚色的信号画报；电影叙事更新为梅紫、杏橙、砖红的浅色电影节节目册 | 图片美术方向必须跟随已通过审美评审的最终排版，而不是沿用被否决的旧版主题 |
| D427 | 新增东方册页、网点剪报、波普丝网、自然图鉴、商业信号和电影分镜六种独立图片能力 Manifest | 能力描述画材、边缘和构图特长，可被任何相近主题通过评分选中，不属于主题私有实现 |
| D428 | 新能力上线不得改变原六套主题在无历史条件下的主要图片风格倾向 | 新增能力不应让已在生产环境验证的主题发生无意漂移 |
| D429 | Provider 编译层必须把色板、表面和构图内部标识翻译为明确中文美术语言 | 避免 `rice_paper_folio`、`paper_white` 等工程标识直接进入 Seedream 提示词造成理解不稳定 |
| D430 | 回归测试同时验证六套新主题的代表性匹配、旧主题稳定性和跨内容动态选择 | 既保证新主题产生差异，也证明系统仍是评分匹配而非隐性一对一绑定 |

## 46. 跨行业内容结构命名与规划来源透明化（D431–D434）

工作台原有“文章类型”容易被理解成教育、科技、商业等行业分类；若改成“文章主题”，又会与文章选题和视觉主题产生新的歧义。当前四个选项实际描述的是文章如何组织信息，因此产品层统一称为“内容结构”，技术层继续兼容既有枚举。

| 决策 | 内容 | 产品理由 |
|---|---|---|
| D431 | 工作台把“文章类型”改为“内容结构”，不使用“文章主题” | “主题”已经同时指向选题与视觉皮肤；“内容结构”更准确表达数据解读、步骤指南、趋势分析和案例叙事的组织方式 |
| D432 | 四类展示名称改为数据与规则解读、教程与步骤指南、观点与趋势分析、故事与案例叙事；内部枚举保持不变 | 面向各行各业时不再依赖教育语境，同时保证旧任务、API 与 Skill 输入继续兼容 |
| D433 | 默认继续自动识别；直接上传 Markdown 使用本地规则，通过 Agent Skill 创建时使用宿主 Agent 语义规划，并在任务页显示规划来源 | 用户不需要额外配置文本模型，也不会把“自动识别”误解成一次隐藏的外部模型调用 |
| D434 | 本地识别词表扩展到监管、指标、流程、品牌、访谈、行业等通用信号 | 让无 Agent 的手动上传路径也能覆盖商业、科技、生活方式和公共议题，而不是偏向教育样本 |

## 47. 工作台首屏与输入审计渐进披露（D435–D438）

真实使用表明：方案生成完成后，六步进度条和完整预检档案几乎不再参与日常操作，却持续占据工作台首屏。输入检查仍是安全能力，但不应在成功状态下压过主题、图片和文章预览。

| 决策 | 内容 | 产品理由 |
|---|---|---|
| D435 | 已生成推荐稿且不存在未解决问题时，默认隐藏六步进度与完整预检卡 | 让编辑区和文章预览成为工作台首屏主体，减少完成状态的过程噪音 |
| D436 | 生成未完成、存在阻断或仍有待确认项时，进度与预检自动展开且不可静默隐藏 | 精简成功路径不能掩盖事实、结构或发布资产风险 |
| D437 | 成功状态在顶栏保留“输入检查通过”入口，可按需展开完整审计信息 | 保留可追溯性，同时采用渐进披露降低普通运营的认知负担 |
| D438 | 输入检查与进度数据继续完整保存，只改变默认展示层级 | 本轮是交互收敛，不削弱 Preflight 能力、宿主规划门禁或旧任务兼容性 |

## 48. 静态流程退场与交付状态单点反馈（D439–D443）

继续评审后确认：六步流程条没有真实动画、耗时反馈或可点击动作，完成后只是在重复系统状态；资产阻断同时出现在预检卡、交付说明和底部清单，也会让用户误以为需要处理三次。工作台应从“展示系统过程”转向“支持完成文章”。

| 决策 | 内容 | 产品理由 |
|---|---|---|
| D439 | 人工评审页彻底移除六步静态流程条，进度数据仅保留给 API、CLI 和故障诊断 | 没有过程反馈和操作价值的步骤条不能改善等待体验，只会挤压工作台主体 |
| D440 | 推荐稿生成后不再展示完整预检档案；只有尚未生成方案或仍需人工确认非资产问题时才出现 | 封面与配图缺失由对应工作区处理，不再在页面上方重复形成第二套入口 |
| D441 | 删除交付区独立的“确认前需要处理”大面板 | 同一阻断不应在预检、交付文案和阻断列表中重复出现 |
| D442 | 保存或创建公众号草稿按钮在条件未满足时保持灰色，并在按钮下方显示最多两条未完成原因 | 用户只需要知道当前能否交付以及下一步缺什么；移动端也不能依赖悬停提示 |
| D443 | 完整发布检查继续保留在折叠的“发布信息与检查详情”中 | 日常路径保持简洁，诊断与高级配置仍可追溯；本轮正式取代 D437 的顶栏审计入口 |

## 49. 发布阻断根因去重（D444–D446）

交付按钮首次使用具体原因提示后，暴露出同一个缺少封面的根因同时被描述为“预检未完成”和“封面未进入受控资产库”。通用状态与具体动作并列会让用户误以为存在两个不同问题。

| 决策 | 内容 | 产品理由 |
|---|---|---|
| D444 | 发布就绪接口按“一个根因、一条可执行提示”输出阻断，不同时返回预检总括与具体资产问题 | 用户应处理真实任务，而不是理解内部检查层级 |
| D445 | 缺少封面、占位封面和原稿图片未导入统一由资产完整性检查给出具体提示 | 这些问题都能在封面或配图工作区直接解决，通用预检提示没有新增信息 |
| D446 | 非资产类预检问题直接返回原始具体文案；只有报告状态异常且找不到未解决项时才使用通用刷新提示 | 既减少歧义，也保留旧数据异常和诊断边界 |

## 50. 内置微信官方 API 发布器与零 Node 用户安装（D447–D451）

真实生产使用已经证明 Visual Director 的冻结 HTML、发布资产和人工确认链路可以独立成立；Wenyan 在当前架构中只承担 access token、图片上传和 `draft/add` 的传输职责，却引入了 Node.js、全局 npm 包、PATH 与第三方版本兼容成本。本轮将传输层收回项目内部，不改变“冻结后人工确认、最终群发仍在公众号后台完成”的安全边界。

| 决策 | 内容 | 产品理由 |
|---|---|---|
| D447 | 从运行时、设置页、Doctor、Skill 和当前安装文档中彻底移除 Wenyan，不保留双发布链路与自动回退 | 两套发布器会增加故障分支、测试矩阵和用户认知负担；当前旧数据没有迁移价值，可直接硬切换 |
| D448 | 使用 Python 内置网络库直接调用微信官方 token、永久图片素材与草稿创建接口 | Visual Director 已经拥有最终内联 HTML 和受控图片资产，发布器只需完成确定性传输，不再依赖外部 CLI 二次渲染 |
| D449 | AppID 与 AppSecret 只保存在本机私有配置；access token 仅做进程内存缓存，不写数据库、日志或诊断响应 | 缩小凭据暴露面，同时避免每张图片重复换取 token |
| D450 | 图片上传失败可重试；`draft/add` 请求超时或连接中断统一标为 `unknown`，禁止自动重试并要求先去草稿箱核对 | 草稿创建不是天然幂等操作，结果未知时自动重试可能制造重复草稿 |
| D451 | 正常用户安装只使用发行包内已构建的工作台，不调用 npm/pnpm；缺少 `dist` 时直接报告发行包不完整，Node/pnpm 仅保留在 CI 和开发构建 | 保留“把 GitHub 链接交给 Agent 即可安装”的体验，同时降低首次安装体积、权限与工具链故障 |

## 51. 微信白名单真实校验与 unknown 可恢复处置（D452–D456）

真实运营暴露出两个相互关联的问题：设置页的“我已加入白名单”只是人工声明，不能证明微信接口当前可用；而 `draft/add` 连接中断进入 `unknown` 后，如果工作台只禁止重试却不给核对后的处置入口，就会把安全门禁变成永久死锁。本轮在不放宽重复草稿风险的前提下收敛状态机。

| 决策 | 内容 | 产品理由 |
|---|---|---|
| D452 | 删除设置页“已加入 IP 白名单”人工勾选项；继续保留公网 IP 检测、复制和微信开发者后台配置指引 | 人工勾选不能替代真实能力校验，还会造成“没勾但能连通”和“勾了但已换 IP”的歧义 |
