# V1.0 开源 Skill 产品定位与发行决策

- 文档状态：D154–D211 已接受
- 产品负责人：徐均舸
- 日期：2026-07-22
- 阶段目标：把现有公众号视觉编译器收口为本地优先、可一行安装、可由 OpenClaw 调用的开源产品

## 1. 产品定义

V1.0 定位为“开源、本地优先的公众号视觉主编 Skill”。运营在 OpenClaw 中输入文章需求，宿主模型按照约定生成结构化初稿；Skill 调用视觉编译器创建任务并打开本地 Web 工作台；运营确认主题、组件、封面和插图后，将成稿同步至微信公众号草稿箱。无法配置公众号接口时，系统提供富文本复制与成稿导出作为降级路径。

Skill 不是单一提示词文件，而是可安装的软件包。建议发行包至少包含：

```text
wechat-visual-director/
├── SKILL.md                 # 触发条件、工作流和宿主模型行为约束
├── scripts/                 # 启动、配置、任务创建和发布脚本
├── app/                     # 视觉编译器、Web 工作台和本地数据
├── templates/               # Markdown 协议、视觉系统与组件资源
├── adapters/                # OpenClaw、图片模型和微信发布适配器
├── references/              # 配置、故障排查与兼容说明
└── manifest/lock files      # 版本、依赖和安装元数据
```

其中 Skill 是宿主 Agent 看得懂并能调用的入口；视觉编译器、Web 工作台和发布适配器是独立、可测试、可复用的核心程序。这一组合统一称为“公众号视觉主编 Skill”。

## 3. 一行安装目标

V1.0 的发行体验目标是让具备 Node.js 环境的用户通过一条命令完成安装和初始化，例如：

```bash
npx wechat-visual-director init
```

或者由 OpenClaw 的 Skill 安装机制从 GitHub 安装：

```bash
openclaw skill install github:<owner>/wechat-visual-director
```

以上命令目前是目标接口，不代表已经发布或可以执行。最终命令需要以 OpenClaw 当前支持的安装规范、包名占用情况和跨平台验证结果为准。

一行命令背后仍会执行多项工作：

1. 检查 Node.js、Python 或已打包运行时；
2. 下载固定版本的 Skill 和核心程序；
3. 创建本地数据目录；
4. 启动配置向导；
5. 安装或注册 OpenClaw Skill；
6. 启动本地 API 与 Web 工作台；
7. 执行健康检查并返回本地访问地址。

因此“一行安装”是发行层对复杂性的封装，不等于项目内部只有一份文本文件。

## 4. 推荐运行模式

### 4.1 OpenClaw 模式（首发）

```text
运营自然语言需求
→ OpenClaw 宿主模型生成规范化 Markdown
→ Skill 创建本地视觉任务
→ 浏览器自动打开工作台
→ 人工确认
→ 微信草稿适配器 / 富文本复制 / 成稿导出
```

宿主模型负责内容生成与结构化输出。视觉编译器继续负责解析、语义纠错、视觉规划、确定性渲染、图片槽、历史避重和质量检查。

### 4.2 独立模式（兼容）

没有 OpenClaw 的用户可以直接启动本地工作台，上传或粘贴 Markdown。独立模式默认使用确定性规划；需要模型增强时由用户自行配置文本模型 Key。

## 5. 配置分级

| 配置 | 是否必需 | 缺失时行为 |
|---|---:|---|
| 本地运行环境 | 是 | 安装器提示并终止，不留下半安装状态 |
| OpenClaw | OpenClaw 模式必需 | 仍可使用独立工作台 |
| 文本模型 Key | 否 | OpenClaw 模式复用宿主模型；独立模式使用规则规划 |
| 图片模型 Key | 否 | 允许上传、沿用原图或跳过配图 |
| 微信 AppID/AppSecret | 否 | 禁用自动草稿，保留复制和导出 |
| 微信接口白名单 | 自动草稿必需 | 配置向导展示检测结果和修复步骤 |

公众号密钥不得写入 `SKILL.md`、模型提示词、对话上下文或前端存储。应保存在本地环境变量、系统凭据存储或不被模型读取的私有配置文件中。

## 6. 开源 MVP 边界

首版必须完成：

- 自然语言需求到规范化初稿的 Skill 工作流；
- 不规范 Markdown 的结构修复与语义保护；
- 本地 Web 排版工作台；
- 多视觉系统、语义组件和最近五篇避重；
- 图片上传，以及可选的 BYOK 生图适配器；
- 本地任务和已确认成稿保存；
- 自动打开工作台；
- 微信草稿、富文本复制和成稿导出三种交付路径；
- 配置向导、健康检查、错误提示和卸载说明；
- Windows 优先的一行安装与从零安装验证。

首版不包含：

- SaaS 用户、团队与权限系统；
- 计费和模型额度转售；
- 云端长期托管；
- 公众号数据看板和 A/B Test；
- 复杂长期记忆、推荐算法和自动偏好学习；
- 多 Agent 平台同时首发。

## 7. 商业化保留边界

开源核心保持本地可用和 BYOK。未来托管版可以围绕无需部署、固定出口 IP、密钥托管、团队品牌资产、多账号协作、稳定发布、模型额度和高级组件收费。核心数据结构、Provider 接口、Publisher 接口和历史存储需要保持可替换，但当前不实现计费逻辑。

## 8. 下一阶段顺序

1. 冻结 OpenClaw Skill 与核心程序的职责边界；
2. 定义自然语言需求到规范化 Markdown/文章结构的输入协议；
3. 将当前 API 与 Web 封装成可由一个启动器管理的本地应用；
4. 实现首次运行配置向导和独立模式；
5. 编写 OpenClaw Skill，打通“创建任务—打开工作台—获得结果”；
6. 接入微信草稿适配器及复制/导出降级路径；
7. 在一台未配置过项目的 Windows 电脑上执行从零安装测试；
8. 清理示例、密钥、许可证和文档后发布 GitHub 仓库。

当前阶段不应先优化 npm 包名、Logo、官网或收费设计。下一项研发工作是第 1、2 步：确定安装后各模块如何协作，以及宿主模型必须输出什么。

### 10.1 当前实现与路线图区分

本文第 1、4、6 节描述的是已接受的 V1.0 产品目标，不代表每项均已在 Alpha 实现。公开 README 和 CLI `doctor` 必须以运行时真实能力为准：

- 已实现：Markdown 预检、规则/可选智能规划、双方案、组件与图片确认、本地任务保存、冻结版本；
- 未实现：真实微信公众号草稿创建、富文本一键复制、最终群发；
- 安全约束：即使未来接入微信发布适配器，最终群发仍需在微信后台由人工确认。

### 10.2 公开仓库门禁

GitHub 首发前必须同时通过：

1. 中性品牌运行验证，页面和新任务不依赖私有资产；
2. 敏感词、密钥模式、二维码和内部样本扫描；
3. 后端测试、前端类型检查/构建、Skill 校验和浏览器主链路回归；
4. `README`、`SKILL.md`、CLI `doctor` 三处能力声明一致；
5. 从 GitHub 克隆后的干净 Windows 环境安装验收。

## 20. Alpha.10 修复决策与真实文章回归记录

本节记录 Alpha.9 发布后的真实使用问题。以下修复范围已于 2026-07-28 接受，纳入 Alpha.10：

| 决策 | 内容 | 产品理由 |
|---|---|---|
| D245 | 持久安装同时注册通用用户级 Skill 与 OpenCode Skill | 新对话不再依赖临时仓库上下文 |
| D246 | OpenCode 增加显式 `/wechat-visual-director` 命令入口 | 自动触发失败时仍有可发现、可解释的确定入口 |
| D247 | 写稿后执行“事实锁定的语义整理” | 把原文真实的并列、步骤、概念和二维数据显式表达出来 |
| D248 | 长分析稿结构过平时阻断自动规划并返回 `source_structure_too_flat` | 不让用户把“原稿没有可绑定结构”误判为组件库失效 |
| D249 | 规划结果暴露候选结构、最终采用组件和编译调整 | 能区分写稿、Brief 和安全编译三个环节的问题 |
| D250 | 渲染器继续禁止擅自拆段、造表和补结论 | 丰富度提升不能以篡改事实和文章逻辑为代价 |

### 20.1 跨会话 Skill 发现

- 现象：同一台电脑在完成安装的原对话中可以运行 `wechat-visual-director`，重新打开 OpenCode 对话后无法自动发现，斜杠菜单中也不存在该 Skill。
- 已定位原因：当前持久安装器只安装视觉主编核心程序，没有把 Skill 入口同步注册到宿主 Agent 的用户级 Skill 目录；原对话依赖临时仓库上下文，因此换对话后丢失发现能力。
- Alpha.10 修复：安装和升级时注册或刷新用户级 Skill；`doctor` 增加 `host_skill_registered` 检查；补充 OpenCode 命令入口，但核心程序继续保持宿主无关。

### 20.2 真实长文组件覆盖不足

复现输入为“贵港工贸职业学院教育资产流拍—民办高校存量博弈—教育发展‘十五五’规划”分析稿。相同选题下：

- 最新 Skill 生成稿主要由 H2、连续正文、行内强调、引文和两张图片组成，只出现章节标题与证据引文等少量视觉部件；
- 最新稿导语与第一章还重复讲述了同一事件，说明写稿阶段除语义扁平外也缺少结构去重；
- 运营调整稿包含真实数据表、并列因素、编号政策信号、原因拆解和行动建议，组件形态与阅读节奏明显更丰富；
- 文章内容本身存在足够的真实结构，问题不属于“选题不适合组件”。

根因位于内容写作与视觉规划之间的结构契约：

1. 当前 Skill 虽要求规范 Markdown，但“不要为了触发组件制造结构”的约束容易让宿主把真实的并列关系、政策影响和数据对比继续写成普通段落；
2. 视觉编译器只允许组件绑定原文已有的 H3、列表、引文和二维表格，不得擅自把连续正文拆成列表或补造比较关系；
3. 因此即使组件库已经丰富，只要写稿阶段输出为“第一、第二、第三”的连续段落，后续 Brief 和渲染器也只能安全降级为普通排版；
4. 该安全降级原则本身应保留，Alpha.10 应修复的是结构化写稿与可观测性，而不是让渲染器改写事实。

Alpha.10 修复：

- 在宿主写稿流程中增加一次“组件友好但事实锁定”的语义整理：真实并列因素使用列表，真实先后步骤使用有序列表，真实二维数据使用表格，概念使用 H3 与紧随定义段；不得为凑组件补造关系；
- 长分析稿若存在大量正文段落，却没有列表、H3、表格或可绑定证据，预检返回 `source_structure_too_flat`，允许宿主基于原有事实进行一次结构整理；
- 规划结果增加候选数、最终采用数及降级原因，区分“原稿没有候选”与“Brief 选择后被安全降级”；
- 本节复现提示词已固化为 `samples/evaluation/realistic/alpha10-private-college-stock-game-regression.json`，后续必须在不依赖旧窗口记忆的新对话中执行。

验收标准：

1. 新对话能够直接发现并调用已安装 Skill；
2. 复现文章至少形成三种有事实依据的结构角色，例如事件证据、行业数据/对比、政策影响或读者行动建议；
3. 不把 H1/H2 吞入组件，不改写数字与来源，不为了视觉效果制造表格、结论或行动建议；
4. 若结构仍不足，系统明确提示原因，而不是让用户误以为组件库失效；
5. 同一复现稿继续通过微信草稿兼容性检查，并保持移动端阅读节奏不过度堆砌。

## 23. 未来科技第二版视觉语法决策（D263–D268）

人工横向评审确认“青春校园”比“未来科技”更有设计感。问题不在未来科技的色彩，而在其大量使用圆角舱、胶囊节点和渐变卡片，导致整篇更像 SaaS 界面而不是公众号编辑设计。因此冻结已通过的青春校园，仅重构未来科技。

| 决策 | 内容 | 产品理由 |
|---|---|---|
| D263 | 青春校园冻结为当前基线 | 已获得用户明确偏好，后续修改不得顺带改变其文章骨架与组件样式 |
| D264 | 未来科技改用 `FUTURE FIELD NOTES` 视觉语法 | 以未来实验档案为记忆点，替代抽象的悬浮软件面板 |

| D268 | 主题重构不改变 `wechat_article.v1` 与事实锁定规则 | 本轮只改确定性渲染器，宿主智能体、组件绑定和微信发布链路无需重新配置 |

## 24. 未来科技第三版“未来科学杂志”决策（D269–D274）

第二版虽然摆脱了 SaaS 圆角面板，但人工评审认为密集蓝色线框、重复英文索引和实验记录语法过强，整体更像工程蓝图，仍不具备公众号文章所需的舒适度与吸引力。本轮继续保留主题辨识度，但把“技术说明书”改为“未来科学杂志”。

| 决策 | 内容 | 产品理由 |
|---|---|---|
| D269 | 未来科技采用 `FUTURE EDITION` 视觉语法 | 用科学杂志的版式气质表达未来感，不再依赖工程制图隐喻 |
| D270 | 以极光色带、错位留白和杂志式大字号建立记忆点 | 未来感来自构图、节奏与色彩氛围，而不是密集线框和技术术语 |
| D271 | 组件提示词优先使用中文语义标签 | “关键问题、证据摘录、进程路径、要点回收”等标签比重复英文编号更符合公众号阅读场景 |
| D272 | 软色块只服务于关键信息，不把每段正文装进圆角卡片 | 在丰富度与长文呼吸感之间保持平衡，避免退回 SaaS 卡片堆叠 |
| D273 | 编号继续根据真实条目动态生成 | 大字号索引可以作为杂志节奏，但不得硬编码步骤数量或替代文章原有层级 |
| D274 | Schema、宿主规划和发布链路保持不变 | 本轮仍是确定性渲染器升级，已安装 Skill 无需改变输入协议或重新配置模型 |

组件库版本保持 `wechat_components.v0.11.0`，渲染器升级为 `preview_renderer.v0.16.0-future-science-editorial`。

## 25. Alpha.11 发布与真实运营观察决策（D275–D280）

六套主题已完成人工评审。下一阶段不继续通过增加模板数量追求表面丰富度，而是把当前能力交给真实运营文章验证，识别问题究竟来自组件供给、原稿结构还是 Agent 选择策略。

| 决策 | 内容 | 产品理由 |
|---|---|---|
| D275 | 当前六套主题进入 Alpha.11 发布基线 | 轻盈阅读、温暖人文、编辑对比、理性网格、青春校园和未来科技均已完成人工评审 |
| D276 | 暂缓扩展到十套主题 | 当前 12 类语义组件已经具备基础供给，继续增加主题不能替代真实采用验证 |
| D277 | 下一阶段观察 3–5 篇真实运营文章 | 用自然选题覆盖长短文章、不同结构和不同模型能力，避免继续只在实验稿中优化 |
| D278 | 保留组件切换，但默认方案必须以直接发布为目标 | 手动切换是安全兜底，不应成为每篇文章的固定必经步骤 |
| D279 | 记录自动方案与运营最终方案之间的修改差异 | 修改位置和原因比单纯“满意/不满意”更能定位产品问题 |
| D280 | 完成真实样本后，再决定优化组件、结构识别或选择策略 | 三类问题的根因和解决方式不同，后续迭代必须由证据驱动 |

真实运营观察只记录最小必要信息：选题/文章类型、系统推荐主题、最终使用主题、自动采用组件数、人工修改位置、从生成到草稿的处理时间、草稿创建是否成功和关键截图。文章正文、公众号密钥及内部品牌资产不进入公开仓库。

## 26. Seedream 5.0 信息图与封面无损适配决策（D281–D286）

Alpha.11 真实链路诊断包证明，正文信息图的缺边已经存在于 Seedream 5.0 Lite 原始输出，正文候选的原始文件与系统保存文件字节一致；封面复用则确实由本地 16:9 到 5:4 的中心裁剪造成信息损失。本轮据此拆分模型构图与本地适配问题：

| 决策 | 内容 | 产品理由 |
|---|---|---|
| D281 | 不把 Seedream 4.0 的字数建议当作 5.0 硬限制 | 5.0 官方建议简洁准确，但复杂信息图仍需要明确内容、版式与风格；应删除重复描述而不是机械截断锁定原文 |
| D282 | 结构信息图使用中央安全区与纵向编辑序列 | 左右各留 12%、上下各留 10%；3–4 个长中文节点禁止横向多栏，避免模型把文字和标题画出画布 |
| D283 | 提示词不得向模型暴露系统字段标签 | 不再使用“节点1/节点2”等词，锁定内容改为自然编号，减少系统词被模型误画进成图 |
| D284 | 信息图背景改为冷白基底，暖色只作局部点缀 | 去除大面积米黄/黄色底偏置，并用开放式分区、细线、手绘标记和边缘插画增强轻盈感 |
| D285 | 正文图片缩略图完整显示，封面复用改为无损适配 | 候选缩略图使用 `contain`；16:9 正文图转 5:4 封面时完整保留原图，以柔化背景填充空余区域，不再中心裁切 |
| D286 | Windows 启动器支持 `pnpm.ps1` | 部分电脑只有 PowerShell shim，CLI 应通过 PowerShell 安全启动工作台，不再要求人工执行 `pnpm.ps1 dev` |

图片提示词版本升级为 `v5-seedream-safe-infographic`。本轮只修改新生成候选，不回写已经冻结或已经创建公众号草稿的历史任务。

## 27. 真实长文组件节奏修复决策（D287–D294）

任务 `cc483b38-5de2-459c-a577-0efddc5b68d5` 的诊断结果表明，主题样本册与真实文章之间的视觉差距并非组件库不足：宿主原本建议了概念解释、相邻段落对比和八项行动清单，但兼容层将三者全部降级；随后覆盖兜底又补入重复的编号观点和警示卡，最终五个组件只有三种形态。

| 决策 | 内容 | 产品理由 |
|---|---|---|
| D287 | 真实稿评测同时检查组件数量、形态多样性与文章分布 | “有五个组件”不能代表视觉节奏合格，重复形态仍会产生模板感 |
| D288 | 概念解释继续禁止消费 H1/H2，但允许短 H3–H6 名词标题与紧随解释段 | “院校专业组”这类中文概念不一定出现“是指/定义为”，不应被机械关键词误杀 |
| D289 | 对比卡允许绑定两段相邻且具有明确成对信号的原文段落 | 支持“盲目勾选/完全不勾选”等真实对照，同时禁止拼接不相邻内容或创造结论 |
| D290 | 行动清单允许标题与列表之间存在引导段，并完整支持 2–10 项 | 公众号长清单常有承上启下段；消费列表后必须渲染全部条目，不能静默丢失第 7、8 项 |
| D291 | 45 个以上内容块的超长文章允许 6 个强组件 | 该密度约为每 8–10 块一个视觉入口，仍低于堆砌阈值；其他中长文章继续保持 3–5 个 |
| D292 | 中长文章目标至少四种组件形态 | 补位优先引入未使用的语义组件，而不是继续重复警示卡或编号列表 |
| D293 | 补位优先覆盖文章尚未出现强组件的前、中、后三段 | 避免视觉重点集中在开头或结尾，使长文滚动节奏更均匀 |
| D294 | 多列数据表继续由主题表格渲染，不强制转换成双栏对比卡 | 表格转换会丢失行列事实；视觉丰富不能以信息损失为代价 |

## 28. 连续概念词条组决策（D295–D299）

| 编号 | 决策 | 原因 |
